# 工程细节与踩坑点清单（面试材料，实现时逐项对照，不许漏）

> 每一条都来自对一个真实企业级 Java Agent 项目及其底层框架真实源码 + 作者本人设计笔记的研读，不是我编的。格式统一：**坑是什么 → 怎么解决 → 为什么值得讲（尤其是 Java 工程角度）**。实现到对应模块时，照着这份清单逐条核对有没有漏掉。

## 一、ReAct Loop 核心

### 1. 流式 tool_call 参数分片重组
- **坑**：Provider 流式返回时，一次工具调用的 JSON 参数被拆成多个 chunk（第一个带 id/name/半截参数，后续只带同 id 的参数续片）。逐个 chunk 单独 JSON.parse 必然失败——半截 JSON 本来就不合法。
- **解法**：按 `id` 做累加器（`Map`/线性扫描均可），纯字符串拼接 `arguments`，**校验放到整轮结束后统一做一次**，不做增量校验。
- **Java 角度**：这是"流式协议 + 结构化数据"组合的通用问题（对应 SAX 解析大 XML、gRPC streaming 反序列化都是同一类模式），面试可以直接类比讲清楚。

### 2. 工具调用参数校验失败的降级策略
- **坑**：分片拼接完仍可能不是合法 JSON（网络截断、Provider bug）。直接抛异常会让整个 ReAct loop 崩掉。
- **解法**：`sanitizeToolCalls` 里捕获解析异常，降级成 `"{}"` 空参数，让工具/下一轮模型自己处理"参数为空"这个情况，而不是让异常穿透整个 reactive 链。
- **Java 角度**：Reactor 链里"哪一层该吞异常、哪一层该往上抛"是个真实的架构判断，这里是"宁可业务降级也不让 loop 整体失败"的例子。

### 3. `<think>` 标签跨 chunk 状态机
- **坑**：MiniMax 类模型把思考内容用 `<think>...</think>` 混进正文，流式返回时标签本身可能被硬切成两半（`<thi` / `nk>`）。
- **解法**：`ThinkTagParser.parse(chunk, inThink)` 把"上次调用结束时是否还在标签内"当参数传入，返回值也带上最新状态，靠调用方（`RoundState.inThink` 字段）在多次调用间串行传递。
- **Java 角度**：有限状态机 + 跨调用状态传递，是流式解析器的标准写法（类似写一个增量 XML/JSON tokenizer）。

### 4. reasoning_content 提取的反射缓存
- **坑**：不同 Provider 把"思考内容"放在不同地方——标准的走 metadata map（`reasoningContent`/`reasoning_content` 两种 key 都要试），特殊的（如 DeepSeek 的 Spring AI 封装）只能反射调用具体子类的 `getReasoningContent()`。
- **解法**：反射结果（`Method` 对象）**按 Class 缓存**（`volatile Method reasoningContentGetter` + `volatile Class reasoningContentGetterClass`），避免每个 chunk 都重新 `getMethod` 查找。
- **Java 角度**：反射性能优化的经典手法（缓存 `Method`/`Field` 对象），双重检查 + volatile 保证可见性，面试问"反射为什么慢、怎么优化"直接有实例。

### 5. DeepSeek `reasoning_content` 强制回传（Spring AI 1.x 的已知坑，2.0 上为部分修复）
- **坑**：DeepSeek-V4 系模型开启 thinking 模式时，**上一轮返回的 `reasoning_content` 必须原样回传给下一轮 API**，否则直接 HTTP 400。Spring AI 1.x 的原生 `DeepSeekChatModel` 没处理这个回传逻辑，导致"第一轮成功、工具执行后第二轮直接 400，ReAct loop 卡死"。
- **解法**：自己包一层 `ChatModel` 装饰器，在构造下一轮请求时把上一轮的 `reasoning_content` 塞回消息体。
- **本项目行动项**：**必须在实现前先验证 Spring AI 2.0 是否已经修好这个问题**（2.0 全面切换到官方 SDK，有可能已经解决，也有可能还在）——这是一个会直接导致 P0 功能不可用的隐患，不能假设它已经修复。

#### 5a. Spring AI 2.0.0 上的验证结论：**部分修复**

调研方式：反编译/比对 `spring-ai-deepseek` 1.1.0 / 1.1.8 / 2.0.0 的官方 sources jar，加上 `spring-ai-model` 2.0.0、`spring-ai-client-chat` 2.0.0，再对照上游 issue/commit。**没有调真实 API**，所以结论分成"静态证据充分"和"需要实测确认"两档，下面逐条标注。

**① 序列化这一半修好了（证据充分）**

`DeepSeekChatModel#createRequest` 的 ASSISTANT 分支，1.x 一直把 `ChatCompletionMessage` 的第 7 个参数（`@JsonProperty("reasoning_content")`）写死成 `null`；2.0.0 改成从消息里读出来回传：

```java
// 2.0.0：spring-ai-deepseek 的 DeepSeekChatModel#createRequest
String reasoningContent = null;
if (message instanceof DeepSeekAssistantMessage deepSeekAssistantMessage) {
    reasoningContent = deepSeekAssistantMessage.getReasoningContent();
    ...
}
return List.of(new ChatCompletionMessage(text, Role.ASSISTANT, null, null,
        toolCalls, isPrefixAssistantMessage, reasoningContent));
```

上游 commit `e2486b1`（2026-05-25，"Fix reasoning_content lost with Deepseek"，closes GH-6118 / GH-6143），随 2.0.0-RC1 进入 2.0 线。**没有回合到 1.x**——已核对到 1.1.x 线最新的 1.1.8，那一行仍然是 `null`。GH-6026 这张原始 issue 至今还挂着 open，光看 issue 状态会误判成"没修"，必须看代码。

**② 但触发条件很窄，默认命中不了（证据充分）**

`reasoningContent` 是 `DeepSeekAssistantMessage` 这个**子类的私有字段**，既不在 `AssistantMessage.metadata` 里，基类 `AssistantMessage` 在 2.0.0 里也压根没有任何 reasoning 相关字段。于是上面那段 `instanceof` 判断，只在"放进历史的那个消息对象**仍然是 `DeepSeekAssistantMessage` 实例且字段没丢**"时才成立。现实中三条路里有两条不成立：

- **非流式**：`DefaultToolCallingManager#buildConversationHistoryAfterToolExecution` 是原样 `messages.add(assistantMessage)`，子类型和字段都留着 → **修复生效**。
- **流式**：2.0 把工具循环从 ChatModel 里挪到了 `ToolCallingAdvisor`，它递归下一轮之前先走 `ChatClientMessageAggregator` → `MessageAggregator`，而 `MessageAggregator` 的收尾是无条件 `AssistantMessage.builder()...build()`——**子类型被抹平成基类，`reasoningContent` 整个丢掉**（它只认 Gemini 风格的 `isThought`/`thoughts` metadata 约定，不认 reasoning 字段）→ **修复不生效**。
- **自己手写 loop（本项目 ADR-0002 的路线）**：历史消息是我们自己拼的。`AgentLoopExecutor#finishRound` 现在写的是 `AssistantMessage.builder().toolCalls(toolCalls).build()`——基类实例、也没带 reasoning → **修复不生效**。

也就是说：SDK 把"怎么序列化"这一半修好了，"谁来保证消息对象里还带着 reasoning"这一半仍然是调用方的责任。**流式 + 工具调用**这个组合——恰好就是 ReAct loop 的默认形态——在 2.0.0 上仍然会丢 `reasoning_content`。

**③ 走 OpenAI 兼容端点访问 DeepSeek 在 2.0.0 上更糟（证据充分）**

2.0 的 OpenAI 模块换成了官方 openai-java SDK，`reasoning_content` 落进 `Delta._additionalProperties`，`ChunkMerger` 不复制它，`AssistantMessage` 也没地方存 → **流式和非流式都拿不到**（上游 GH-6230 / GH-6484 / GH-6558，均针对 2.0.0 复现）。相关修复挂在 **2.0.1 里程碑**（PR #6373 等），而 2.0.1 尚未发版，Maven Central 上 2.0 线的最新正式版就是 2.0.0。结论：**要用 thinking 模式，就得走 `spring-ai-deepseek` 官方模块，不能图省事用 OpenAI 兼容接口**。

**④ 需要实测才能定论的部分**

静态分析能证明"字段在某条路径上被丢了"，但**不能证明 DeepSeek 服务端在这种情况下一定回 400**——服务端的校验条件（哪个模型、是否带 tool_calls、thinking 是否开启）只能实测。实测方案：

1. 拿一个能开 thinking 的 DeepSeek key，用 `spring-ai-deepseek:2.0.0` 的原生 `DeepSeekChatModel`；
2. **Case A（非流式）**：`call()` 一轮拿到带工具调用的响应 → 原样把 `response.getResult().getOutput()` 塞进历史 → 再 `call()` 一轮。预期成功（验证 ① 的结论）；
3. **Case B（同上但先降级消息类型）**：把第 2 步的输出换成 `AssistantMessage.builder().content(...).toolCalls(...).build()` 再发第二轮。预期 400，错误文案含 "The `reasoning_content` in the thinking mode must be passed back to the API."（验证 ② 的结论，也是本项目手写 loop 当前的形态）；
4. **Case C（流式）**：`stream()` + 工具调用走完两轮，看是否 400。
5. 三个 case 都记录**原始 HTTP 请求体**（打开 `spring-ai` 的 request 日志或挂一个抓包代理），直接看 assistant 消息里有没有 `reasoning_content` 字段——比看异常文案可靠。

**⑤ 顺带发现的两个会先于 400 炸掉的问题（证据充分，属于同一次接线要一起解决的）**

- `createRequest` 在 2.0.0 里对 assistant 消息加了 `Assert.state(text != null, "text must not be null")`。而 thinking 模式的工具调用轮 `content` 本来就可能是 null，`AssistantMessage.builder()` 不显式 `.content()` 时 `getText()` 也返回 null → **`IllegalStateException`，请求根本发不出去**。拼历史消息时必须显式给空串。
- 2.0 取消了 ChatModel 层对 options 的 `copyToTarget` 合并（commit `836d691`"Restore options replacing instead of merging in ChatModel"），`createRequest` 直接 `(DeepSeekChatOptions) prompt.getOptions()` 硬转。`LlmInvoker` 现在每轮传的是通用 `ToolCallingChatOptions` → **`ClassCastException`**。要么按 provider 传具体 options 类型，要么由装饰器负责换。

**⑥ 对本项目的行动项**

装饰器**还是要写**，但职责比 1.x 时代小了一大截：1.x 要整段重写 `createRequest`，2.0 只需要保证两件事——**(a)** 把每轮流式聚合出来的 reasoning 重新包成 `DeepSeekAssistantMessage`（或等价地规范化进 metadata 再由装饰器还原）后放进历史，**(b)** 顺手解决 ⑤ 的两个类型问题；序列化那一半交给 SDK。

另外 `ThinkingModeProcessor#reasoningOf` 目前只读 metadata、明确拒绝反射兜底——这个取舍本身没问题，但要注意它**在 2.0.0 上对 DeepSeek 官方模块直接失效**（字段在子类上，metadata 里没有），所以"由该厂商的 ChatModel 装饰器把字段规范化进 metadata"这句注释不是可选项，是必须落地的前置条件，否则 `Thinking` 事件一个都发不出来。

### 6. 上下文压缩占位符必须是合法 JSON，不能是自然语言（真实生产 bug）
- **坑**：早期版本用 `[之前用过 read_file，结果 3200 字符]` 这种自然语言占位符替换旧工具结果，导致模型把它当结构化数据解析，某些 Provider 校验 tool response 格式直接返回 400。
- **解法**：统一成 `{"compacted":true,"tool":"X","originalLength":N,"message":"..."}` 的 JSON 结构，工具调用参数和工具返回结果**两个方向都要压缩**（只压一边，早期版本漏了另一边）。
- **Java/工程角度**：这是"接口契约一致性"问题——同一个消息历史里，有的字段是自然语言、有的是 JSON，消费方（无论是模型还是代码）处理起来必然出岔子。

### 7. 上下文压缩为什么从"保留最近 N 条 + 摘要旧的"改成"全部压缩"
- **坑**：选择性保留最近 N 条，会遇到边界对齐问题——`ToolResponseMessage` 不能脱离它对应的 `AssistantMessage` 工具调用单独存在（很多 Provider API 会拒绝），一旦保留窗口的切点落在一对 tool_call/tool_response 中间，就要往回找边界，多工具调用场景（一个 AssistantMessage 对应多个 ToolResponseMessage）更复杂；而且半压缩半原文的上下文会让模型产生认知断层（引用了一个被压缩掉的结论）。
- **解法**：**全部压缩，不做选择性保留**——从根上消除边界对齐问题，且摘要用的 LLM 自己有判断力去保留真正相关的信息，实测比机械保留最近 N 条效果更好。
- **面试角度**：这是一个"复杂度换来的收益不成正比，反而应该做减法"的真实案例，能讲清楚这个演进过程本身就是加分项。

### 8. 摘要生成时禁止对工具内容做二次截断（真实生产 bug）
- **坑**：早期版本把喂给摘要 LLM 的 `ToolResponse` 内容截到 500 字符，结果 `write_file` 写了一个 3000 字符的完整脚本，摘要 LLM 看到被截断的 500 字符就在摘要里写"这个文件只写了一部分"——一个假的失败结论，污染了后续所有轮次。
- **解法**：`buildConversationText` **不做二次截断**——因为 micro_compact 已经把老工具内容压成了 ~80 字符的占位符，剩下没被截断的都是"最近的、真正需要完整保留的"内容。
- **面试角度**：多层处理管道里，每一层都要清楚自己的职责边界，"上一层已经处理过的东西，这一层不要重复加工"。

### 9. AgentTaskManager：Disposable 必须每轮重新注册
- **坑**：如果只在第一轮注册 `Disposable`，用户中途调用 interrupt/stop 拿到的是第一轮的 Disposable——第二轮真正在跑的订阅根本没被取消。
- **解法**：**每一轮**都重新调用 `setDisposable`，覆盖掉旧的引用。
- **Java 角度**：这是"持有过期引用导致资源泄漏/控制失效"的经典并发坑，Reactor 的 `Disposable` 链路管理本质上和"线程池任务句柄要不要更新"是同一类问题。

### 10. `stopTask` 用原子 `remove` 而不是 `get` 再 `remove`
- **坑**：`get(id)` 判断存在 → `remove(id)` 两步操作之间，可能有新任务插进来注册到同一个 id，导致误删了别人的任务。
- **解法**：直接用 `ConcurrentHashMap.remove(id)` 的原子返回值判断"删没删到"，不做 check-then-act。
- **Java 角度**：并发容器的 check-then-act 竞态是面试高频题，这里是一个真实工程实例，不是背概念。

## 二、Redis 分布式任务管理（多实例部署）

### 11. instanceId 所有权校验后才能续 TTL → 见 #30
本条与 #30 是同一个坑，完整版（含"校验+续期必须是同一个原子操作、不能拆成两条 Redis 命令"这个关键点）在 #30，此处不再重复以免两份解法漂移。

### 12. 前端"停止"要双路径：AbortController + HTTP Pub/Sub 兜底
- **坑**：只做 `AbortController.abort()` 断开 SSE 连接，只能覆盖"前端还连着某个实例"这一种情况；网络已经悄悄断掉、或者后台管理台要强行终止别人的任务，这两种场景 abort 完全无能为力。
- **解法**：两条路径都留着——`abort()` 处理常见情况（毫秒级生效），Redis Pub/Sub 广播处理异常情况（连接已断/跨实例强制终止）的兜底。
- **面试角度**："同一个问题的两种失败模式需要两种独立的应对机制，不能用一种方案覆盖所有场景"——这是系统设计的常见考点。

## 三、ToolSearch 延迟工具发现

### 13. 请求隔离：每次执行都是全新的 discoveredNames 集合
- **坑**：如果 ToolSearch 发现的工具集合是跨请求共享的，会导致请求 A 搜到的工具"泄漏"到请求 B——权限/上下文污染。
- **解法**：每次新的 loop 执行都创建一个全新的 `Session`（内含独立的 `discoveredNames` 集合），执行结束即丢弃。
- **Java 角度**：请求作用域状态隔离，本质是"不要用单例/共享可变状态承载请求级数据"这个基本原则的具体案例。

### 14. 发现工具后不会被动态回收
- **坑**：如果每次工具调用后就把"已发现"状态清掉，模型在同一个任务里反复需要同一批工具（比如 SQL 探索：listTables→describeTables→executeSql 循环好几次）时，会不停地重新触发 `tool_search`，浪费轮次。
- **解法**：一旦被发现，在本次请求生命周期内**只增不减**，直到整个请求结束才整体丢弃。
- **面试角度**："设计取舍"的好例子——不是没考虑动态回收，而是评估后发现"按需披露但不过度动态回收"的收益更高。

## 四、Skills 渐进式披露

### 15. 为什么选"单 mega-tool"而不是"list+load 两阶段工具"
- **坑（早期设计的真实教训）**：先做的是 `read_skill(name)` 单独工具 + 技能列表写进 system prompt 的两段式设计，结果模型频繁把技能名称直接当工具调用（比如直接调 `autumnsgrove-pptx()` 而不是 `read_skill("autumnsgrove-pptx")`）——因为技能列表在 system prompt 里、真正可调的工具在另一个 tool schema 里，模型看到一堆"名字"会本能地想直接调用它们。
- **解法**：把全部技能的 frontmatter 直接渲染进**这一个工具自己的 description**里（XML 格式，比 JSON/Markdown 更不容易和周围说明文字混淆），模型"看到工具描述里列着技能→调用这个工具"是同一个上下文，没有跨位置的联想跳跃。
- **面试角度**："顺应模型的直觉而不是对抗它"——这是一句可以直接用在面试里的话，而且背后有真实失败案例支撑，不是空谈。

### 16. Skills 上传解压：临时目录必须建在目标目录下
- **坑**：zip 上传后解压到 OS 默认临时目录（比如 C 盘），再 move 到 skills 目录（比如 D 盘），Windows 下**跨盘符 move 一个非空目录会抛 `DirectoryNotEmptyException`**。
- **解法**：`Files.createTempDirectory(skillsDirectory, "skill-upload-")`——直接在目标目录下面建临时目录，全程同一个盘符，move 操作退化成本地重命名。
- **Java 角度**：`Files.move` 跨文件系统的行为差异是真实踩过的坑，很多人不知道 Windows 下这个限制。

## 五、文件系统类工具（对应路线图 Phase 0.9）

### 17. `write_file` 的文档和实现不一致（一个真实的活 bug，值得作为反面案例）
- **坑**：工具描述文字写"只能创建新文件，文件已存在会报错"，但实际实现用的是 `CREATE, TRUNCATE_EXISTING, WRITE`——**永远会静默覆盖已存在文件**，和文档描述的行为完全相反。
- **面试角度**：这是一个可以直接拿来讲"代码评审要关注文档和实现是否一致"的真实反例——不是我们要犯这个错，而是复刻时**要不要修这个 bug**本身就是一个值得讨论的决策点（保持一致行为便于对比 or 顺手修掉）。

### 18. `edit_file` 的唯一性校验
- **坑**：如果 `oldString` 在文件里出现多次，无脑替换第一个或全部都可能不是用户想要的。
- **解法**：先统计出现次数，`> 1` 次且没有显式要求 `replaceAll` 就直接报错，逼调用方要么提供更多上下文让匹配唯一，要么显式选择替换全部。
- **面试角度**：这是"防止静默的错误批量操作"的具体设计，Claude Code 自己的 Edit 工具也是这个思路。

### 19. 三级编码兜底
- **坑**：Windows 中文环境下，文件编码可能是 UTF-8/GBK/ISO-8859-1 中任意一种，硬编码 UTF-8 读取会乱码甚至抛异常。
- **解法**：`readStringWithFallback` 依次尝试 UTF-8 → GBK → ISO-8859-1，最后一个必然不抛异常（兜底）。
- **Java 角度**：字符编码检测是经典的 Java I/O 面试题，这里是一个务实的"启发式尝试链"而不是真正的编码检测算法（真正检测编码需要类似 ICU4J 的库），可以讲清楚这个权衡。

### 20. BashTool 的"伪持久 shell"
- **坑**：想让 Agent 感觉像在操作一个持续存在的 shell（`cd` 之后后续命令都在新目录执行），但每次工具调用实际上都是全新启动一个子进程，没有真正的持久 OS 进程/pty。
- **解法**：`ShellSessionManager` 只记录 `lastDirectory` 字符串，每次执行命令前**手动拼接 `cd /d "{dir}" && {command}`**（Windows）或 `cd "{dir}" && {command}`（Unix），命令是 `cd` 时执行后回读新目录更新状态。
- **面试角度**："模拟状态 vs 真实持久状态"的经典权衡——用元数据模拟出用户感知到的持久性，而不是真的维护一个长活进程（复杂度和资源开销都低得多）。

## 六、SQL 数据分析能力包

### 21. M-Schema 而不是原始 DDL
- **坑**：把整个数据库的 DDL 原样丢给模型，信息密度低（存储引擎、字符集、索引名等和写 SQL无关的噪声）、缺业务语义（字段注释可能没有或者太简单）、不好扩展（表一多，噪声本身会稀释模型注意力）。
- **解法**：JDBC `DatabaseMetaData` 内省，输出紧凑的 `(字段名: 类型, 描述, 示例值)` 格式，字符串字段异步采样示例值（带超时），敏感字段跳过采样。
- **面试角度**：这是"给模型的上下文不是越多越好，而是越精炼越好"的具体案例，能扣回 Context Engineering 那套理论。

### 22. SQL 安全校验为什么必须走 AST 而不是正则
- **坑**：正则匹配危险函数（如 `LOAD_FILE()`）两头堵不住——字符串字面量里包含 `LOAD_FILE() demo` 这种文本会被误伤（假阳性）；MySQL 允许函数名和括号之间插注释（`LOAD_FILE/**/('...')`）能绕过正则（假阴性）。
- **解法**：用 JSqlParser 解析成 AST，用 Visitor 模式（`DangerousFunctionFinder extends TablesNamesFinder`，重写 `visit(Function)`）在语法树节点类型层面判断——`Function` 节点才是真正的函数调用，`StringValue` 节点里的文本不会被误判。
- **Java 角度**：AST/Visitor 模式是编译原理相关的经典设计模式，这里直接落地到一个安全校验场景，讲清楚"为什么正则在这个场景下从原理上就不够用"是很扎实的技术回答。

### 23. `executeSql` 六层防御，每一层都假设前一层可能被绕过
- **坑**：`validateSql` 是模型自己选择性调用的工具，ReAct 场景下模型完全可能跳过它直接调 `executeSql`。
- **解法**：`executeSql` 内部**无条件重新跑一遍**安全校验，不信任调用方是否已经校验过；再加只读连接 (`setReadOnly` 仅作提示)+ `TYPE_FORWARD_ONLY/CONCUR_READ_ONLY` 结果集（阻止 `updateXxx` 回写）+ 查询超时 + `setMaxRows(N+1)`（多查一行，靠这一行有没有出现来判断是否被截断，不用再多发一次 `COUNT(*)` 查询）。
- **Java 角度**：`setMaxRows(N+1)` 这个技巧是很实用的 JDBC 细节，"用一次查询顺便判断有没有更多数据"比"先查 COUNT 再查数据"节省一次往返，值得单独拎出来讲。

### 24. JDBC 异常按 SQLState 分类，不同类别不同应对
- **坑**：所有 SQL 异常都当同一种处理，要么全部重试（浪费时间在语法错误上重试）要么全部直接报错（网络抖动这种瞬时错误本可以自动恢复）。
- **解法**：按 SQLState 分类成 TRANSIENT（自动重试 2 次，指数退避）/SCHEMA（提示模型重新调 `describeTables`）/SYNTAX/FATAL，每类给模型不同的、可操作的修复建议文本。
- **Java 角度**：`SQLException.getSQLState()` 分类处理是真实数据库中间件都会做的事，能讲出这个层级说明对 JDBC 有实际使用深度，不是只会用连接池框架。

### 25. 结果集列名要用 `getColumnName`/`getTableName`，不能只用 `getColumnLabel`
- **坑**：脱敏逻辑如果只按查询结果里显示的列名（`getColumnLabel`，会受 `AS` 别名影响）匹配敏感字段名单，`SELECT password AS pwd FROM sys_user` 这种别名查询会绕过脱敏——显示列名是 `pwd`，不在名单里。
- **解法**：额外读取 `ResultSetMetaData.getColumnName()`（真实源列名）和 `getTableName()`（源表名），按真实来源匹配，不依赖显示别名。
- **Java 角度**：`ResultSetMetaData` 这几个方法的语义区别（Label vs Name）是很多人写 JDBC 代码时不会深究、但一旦用于安全校验就必须搞清楚的细节，是很好的追问点。

### 26. 权限模型 AST 改写：为什么不能字符串拼接
- **坑 1（运算符优先级）**：字符串拼接 `原SQL + " AND dept_id IN (...)"`，如果原 WHERE 里有 `OR`（比如 `status=1 OR amount>100`），拼接后变成 `status=1 OR amount>100 AND dept_id IN(...)`，运算符优先级导致 `status=1` 这个条件完全不受权限过滤约束——**权限直接被绕过**。
- **坑 2（LEFT JOIN 语义破坏）**：权限条件如果是对 `LEFT JOIN` 右表加的，放进 `WHERE` 会让右表不匹配/被过滤掉的行连带左表的行也被整体过滤掉——`LEFT JOIN` 退化成了 `INNER JOIN`，这不是权限收紧，是查询语义直接被破坏。
- **解法**：解析成 AST，权限条件作为 `Expression` 节点插入，插入位置按 JOIN 类型判断——普通表/INNER JOIN 的条件放 WHERE，LEFT JOIN 右表的条件必须放到那个 JOIN 自己的 `ON` 子句里。
- **面试角度**：这是这份清单里技术含金量最高的一条——两个坑都是"看起来对、实际上要么不安全要么改变语义"的真实陷阱，能完整讲出这两个坑和对应解法，基本能证明对 SQL 语义和 AST 操作有真正的理解，不是背了个"用 AST 不用字符串拼接"的结论。

### 27. 业务术语消歧为什么用精确匹配不用向量检索
- **坑**：向量相似度检索容易把"活跃客户"和"高价值客户"这种**表面相似但业务定义完全不同**（一个是行为频率、一个是消费金额）的词匹配到一起——一个似是而非的错误匹配比"没匹配到"更危险，因为它看起来很合理，容易被忽略。
- **解法**：精确匹配 term，精确匹配同义词（同义词是人工维护的，不是模型学出来的），匹配不到就诚实返回"没找到，这是全部术语列表"。
- **面试角度**："宁可不匹配也不能匹配错"——这条原则本身就是一个可以直接用在很多场景的设计哲学。

### 28. 数据的时间和现实的时间是两回事
- **坑**：sakila 是冻结在 2005 年的历史样本库，如果"近3个月"按代码运行时的 `NOW()` 计算，结果永远是空的（因为数据集里根本没有"最近3个月"这个时间段的数据）。
- **解法**：把"当前时间"定义成 `MAX(rental_date)`（数据集里实际的最新时间点），而不是系统时钟。
- **面试角度**：这是一个容易被忽略、但在任何"历史快照型"数据分析场景（离线数仓、审计日志分析）都会真实遇到的问题。

### 29. 从来不让 LLM 自己做算术，也不让它用 Bash 绕过工具栈
- **坑（真实教训）**：早期让模型自己写 Python 脚本、通过 Bash 执行来做复杂计算，一是浪费大量 token，二是模型会顺手用 Bash **直接连数据库执行探测查询**——完全绕开了前面辛苦搭的安全校验/权限模型/脱敏这一整套工具栈。
- **解法**：批量聚合永远推给 SQL（`SUM`/`GROUP BY`），最终的标量公式计算（环比、百分比这种）交给一个专门的、输入输出严格约束的 `calculate` 工具；**明确不给这个 Agent 挂 Bash 工具**。
- **面试角度**："给 Agent 一个工具，等于给了它一条绕过所有治理措施的路"——这条原则直接呼应前面 Governance 层设计的核心理由，是一个能贯穿全场景的论点。

## 七、集群部署与多实例工程（Redis 化之后才会真正遇到的坑）

### 30. TTL 续期必须先做归属校验（#11 指向本条）
- **坑**：实例 A 定时续期自己持有的 Redis key，如果不检查"key 里存的还是不是自己的 instanceId"，会出现这种时序：A 因为网络抖动被判定失联 → 实例 B 合法抢占了这把锁并开始处理该会话 → A 的网络恢复，定时任务照常触发续期 → **A 把 B 刚抢到的锁的 TTL 续了一遍**，B 反而变成随时可能被踢的一方。
- **解法**：`compareAndSet(instanceId, ...)` 语义——续期前用 Lua 脚本（或 Redisson 自带的原子操作）保证"读取+比较+续期"是一个原子操作，不是"读一下、Java 里 if 判断、再调续期"这种非原子的三步走（后者本身也是一个竞态窗口）。
- **Java/分布式角度**：这是"分布式锁续期的原子性"问题，直接对应 Redisson 的 watchdog 机制内部要解决的问题；能讲出"为什么校验和续期必须是同一个原子操作，不能拆成两条 Redis 命令"，是分布式系统这块的加分项。

### 31. 优雅关闭：主动释放而不是等 TTL 过期
- **坑**：实例正常下线（滚动发布、扩缩容）时，如果什么都不做，它持有的所有 Redis key 要等 TTL（比如 30 分钟）自然过期，这段时间里这些会话在其他实例上完全"卡死"——用户中途请求会一直被判定为"已有任务在跑"。
- **解法**：`DisposableBean.destroy()` 钩子里主动做三件事——取消 Pub/Sub 订阅、停掉本实例的 TTL 续期定时任务、**主动删除自己持有的全部 Redis key**（而不是留给 TTL 自然过期），这样其他实例能立刻接管。
- **Java 角度**：Spring 的 `DisposableBean`/`@PreDestroy` 生命周期钩子是容器优雅关闭的标准入口，这里是把"业务层面的资源释放"（不只是关连接池）也挂到这个钩子上的具体例子——很多人只记得用它关数据库连接池，忘了分布式协调数据也要主动清理。

### 32. 滚动发布/扩缩容下，进行中的任务怎么办
- **坑**：K8s 滚动发布时 Pod 会收到 `SIGTERM`，默认宽限期（比如 30 秒）内如果长任务（比如 DeepResearch 的多轮 plan-execute 循环）还没跑完，会被 `SIGKILL` 强制杀死——任务状态卡在"进行中"，但实际进程已经不存在了，Redis 里的锁全靠 TTL 才能兜底。
- **解法方向（按需实现）**：`@PreDestroy`/`SmartLifecycle` 里判断"当前实例是否还有在跑的任务"，主动延迟关闭（在 K8s 的 `terminationGracePeriodSeconds` 范围内等在跑任务收尾，或者主动触发 checkpoint/PauseState 快照后再退出），而不是任由 SIGKILL 硬杀。
- **面试角度**：这是"有状态服务在无状态编排平台（K8s）上部署"的经典矛盾点，能讲清楚"用 PauseState 快照把有状态的执行过程变成可恢复的"这个思路，是加分项。

### 33. 数据库连接池要按实例数重新算，不能每个实例都按单机配置
- **坑**：单机验证时数据库连接池配了 `maximumPoolSize=50`，如果数据库自身 `max_connections=100`，扩容到 5 个实例、每个还是配 50，总连接数瞬间冲到 250，数据库直接拒绝新连接。
- **解法**：连接池大小 = (数据库总连接数上限 × 安全系数) / 实例数，配置里做成可由部署环境覆盖的参数，而不是写死的常量。
- **Java 角度**：HikariCP 连接池调优的基本功，面试问"连接池怎么配"很容易只答"调大点"，这里能讲出"为什么调大不是无脑操作、和实例数量的关系"，是更扎实的回答。

### 34. 工具执行的幂等性边界：中断快照不保证工具没有副作用
- **坑**：`SafePoint.TOOL_EXECUTION` 阶段的语义很微妙——中断发生时，工具调用可能已经**部分执行完成**（比如一次数据库写入已经提交、一次外部 API 调用已经发生）。快照恢复时如果简单地"重新执行同一个 pendingToolCall"，对于非幂等操作（写库、发消息、扣费）会造成重复执行。
- **解法**：框架层面（`PauseState`/`SafePoint`）只负责**记录**中断发生时处于哪个阶段，**不保证**工具本身的幂等性——这个责任被显式地留给了工具实现方。也就是说：写类工具必须自己设计成幂等的（比如带业务唯一键做 upsert，或者先检查"这个操作是否已经执行过"再执行），框架不会替你兜底。
- **面试角度**：这是一个容易被忽略但很值钱的边界声明——很多人以为"框架支持断点恢复"就意味着"什么都安全"，能讲清楚"恢复框架管的是执行流程状态，幂等性是业务方的责任"这个边界划分，说明真正理解分布式系统里"至少一次"语义的含义。

## 八、完整数据权限模型的工程细节（对应路线图 Phase 2 的权限模型）

### 35. userId 必须在跨线程池之前被强制固化
- **坑**：Web 层（比如 Spring Security/Sa-Token 的认证上下文）通常是 `ThreadLocal` 存的，只在当前请求线程有效。ReAct loop 一旦为了流式/异步而把执行切到别的线程池（`Schedulers.boundedElastic()`），**认证上下文不会自动跟过去**——如果权限过滤逻辑这时候才去读"当前登录用户"，读到的是空/默认值。
- **解法**：在请求刚进来、**还在原始线程**的时候，就把 `userId` 从认证上下文里取出来，塞进显式传递的参数对象（`RunnableParams`）里，后续无论切到哪个线程，都从这个显式参数读，不依赖 `ThreadLocal` 隐式传播。且这个 `userId` 一旦确定，**不信任模型后续在工具调用参数里生成的任何 `userId` 值**——工具执行前统一用固化的真实值覆盖掉。
- **Java 角度**：`ThreadLocal` 在响应式/异步场景下失效是一个经典坑（很多人做了线程池切换却忘了上下文不会自动传播），这里的解法本质是"把隐式的、线程绑定的状态改造成显式的、随数据流传递的参数"——这是响应式编程里处理"请求作用域数据"的标准思路（对应 Reactor Context / gRPC 的 metadata 传递）。

### 36. 部门树用路径字符串而不是递归查询
- **坑**：要查"某部门及其所有子部门"，如果部门数据是父子 ID 的邻接表结构，朴素做法是递归查询或者应用层 BFS/DFS 遍历——数据量大时是 N+1 查询的重灾区。
- **解法**：给每个部门额外维护一个 `ancestors` 路径字符串字段（比如 `0,100,201,210`，代表从根到当前节点的完整路径），查"某部门及子树"就退化成一条 `WHERE ancestors LIKE '0,100,201,210,%'`——一条 SQL 搞定，不用递归。
- **Java/SQL 角度**：这是"用空间换时间、用简单数据结构替代递归查询"的经典物化路径（Materialized Path）模式，属于树形结构在关系数据库里落地的标准技巧之一（另外两种是邻接表+递归 CTE、嵌套集合模型），能对比讲出三种方案的取舍就是加分项。

### 37. 多角色取并集里"最宽权限"具体怎么算
- **坑**：一个用户可能同时挂多个角色（比如既是"部门经理"又是"审计员"），每个角色的 `data_scope` 可能不一样（一个是 DEPT_AND_SUB，一个是 SELF）。如果实现时随手取"第一个角色的 scope"或者取"最窄的"，都会导致该用户实际能看到的数据范围不对。
- **解法**：明确定义 scope 的宽松度排序（`ALL > DEPT_AND_SUB > DEPT > SELF`），用户最终生效的 scope 取**所有角色里最宽的那一个**；可见部门集合同理，取所有角色各自计算出的可见部门集合的**并集**，不是交集。
- **面试角度**：多角色权限合并规则本身就是一个常见但容易讲错的点（很多人会下意识觉得应该"取交集更安全"，但业务语义上"拥有多个角色应该获得多个角色权限的并集"才是通常预期），能讲清楚这个语义判断本身有价值。

## 九、可观测性的工程细节（对应路线图 Phase 3 的可观测性）

### 38. TTFT（首字延迟）要单独埋点，不能只看总耗时
- **坑**：流式场景下，总响应时间可能是 8 秒，但如果首字延迟就要 6 秒，用户体验上"感觉卡住了"——只监控总耗时这一个指标完全看不出这个问题，聚合报表上"平均耗时 8 秒"看起来还行，实际用户等待体验很差。
- **解法**：在流式响应链路里显式埋两个时间点——请求发出时刻、**收到第一个非空 chunk 的时刻**——两者之差就是 TTFT，作为独立指标单独监控，不和总耗时混在一起看。
- **面试角度**：这是流式/实时系统里的核心体验指标，能主动提出"不能只看总耗时、要单独测 TTFT"，说明真正做过对用户可感知延迟的分析，不是只会套用 APM 工具的默认仪表盘。

### 39. Reactive 链路跨线程调度后，日志上下文/追踪上下文默认不会自动传播
- **坑**：用 MDC（`Mapped Diagnostic Context`，日志框架常用来在日志里带上 `traceId`/`conversationId` 等上下文）配合 SLF4J 打日志时，MDC 本质也是 `ThreadLocal`。一旦 Reactor 把执行切到 `Schedulers.boundedElastic()` 的其他线程，**MDC 里的内容不会跟过去**——切线程之后的日志会丢失 `traceId`，追踪链路断掉。
- **解法**：用 Reactor 的 `Context`（响应式场景下专门设计用来替代 `ThreadLocal` 跨线程传递上下文的机制）或者 Micrometer 的 `ContextRegistry`/`ContextSnapshot` 机制，在调度切换的地方显式做一次上下文快照/恢复，而不是假设 MDC 会自动跟着走。
- **Java 角度**：这是"响应式编程和基于 `ThreadLocal` 的传统上下文传递机制不兼容"这个通用问题在可观测性场景下的具体表现，能讲清楚"为什么 Reactor 需要自己的 `Context` 抽象、它和 `ThreadLocal` 解决的是同一类问题但实现机制完全不同"，是响应式编程这块的硬核加分项。

## 十、MCP Server 生产化检查清单（对应路线图 Phase 9）

### 40. Server 初始化失败必须可观测
- **坑**：现实中大量"工具没出现在模型可选列表里"的问题，根因其实是 MCP Server 在**初始化握手阶段就失败了**（鉴权失败、端口冲突、依赖服务没起来），但因为初始化失败通常只是安静地不注册任何工具，运行时表现就是"这个工具好像不存在"——排查时很容易先去怀疑模型/prompt，绕了一大圈才发现是握手阶段的问题。
- **解法**：初始化阶段的失败必须显式记录日志+暴露成一个可查询的健康状态（比如 `/actuator/health` 里带上每个 MCP Server 连接的状态），而不是安静失败。
- **面试角度**：这是"配置好了但功能没生效"这类问题的通用排查方法论——先看初始化/握手阶段，不要一上来就怀疑运行时逻辑，能讲出这个排查顺序本身就是经验的体现。

### 41. 文件类工具目录白名单、数据库类工具参数化查询，是 MCP Server 暴露给外部 Host 时的最低安全线
- **坑**：MCP Server 一旦对外暴露（可能被 Claude Code、Cursor 等任意支持 MCP 的宿主接入），"信任调用方会好好使用"这个假设不再成立——文件类工具如果不限制目录范围，等于把整个文件系统暴露出去；数据库类工具如果允许拼接 SQL 而不是强制参数化，就是一个现成的 SQL 注入入口。
- **解法**：文件工具强制目录白名单（复用 Phase 0.9 `FileSystemTools` 的 `virtualMode` 沙箱设计）；数据库工具永远走参数化查询或者复用 Phase 2 已经做的 `SqlSafetyGuard`；高危操作一律走 PreToolUse Hook 审批，**不依赖 Server 自己判断"要不要执行"**——审批逻辑要在 Hook/宿主侧统一收口，不能让每个 Server 各自为政。
- **面试角度**：这条直接呼应"对外暴露能力"和"内部使用工具"的安全边界完全不同——同一个工具，内部用时可以信任调用方，一旦变成 MCP Server 对外暴露，威胁模型整个变了，这是评估"要不要把某个能力做成 MCP Server"时必须过一遍的安全清单。

## 十一、多 Agent 编排的工程细节（对应路线图 Phase 8）

### 42. Reviewer 否决机制需要明确的二元判定，不能只是"再问一次模型"
- **坑**：如果 Reviewer Agent 只是简单地把 Specialist 的输出重新丢给模型问一遍"这个对不对"，得到的是又一段自然语言评论，没有清晰的"通过/否决"边界，下游代码没法基于这个结果做分支决策（到底该展示给用户还是拦下来）。
- **解法**：Reviewer 的输出走结构化格式（比如 `{approved: boolean, reason: string, riskLevel: enum}`），下游代码基于 `approved` 字段做硬分支，`reason` 只是给人看的辅助信息，不参与逻辑判断。
- **Java 角度**：这是"让 LLM 输出可以被代码消费的结构化数据，而不是只能给人看的自然语言"这一原则的又一次体现（和 Phase 2 里 `calculate` 工具"不让 LLM 自己算术"是同一类思路——把需要精确判定的环节从"靠模型自觉"改成"靠代码强制"）。

### 43. Workflow Graph 还是自由 Agent Loop，选型标准是"执行路径能否提前确定"
- **坑**：不管什么场景都上图执行器（Workflow Graph），会把简单场景过度设计复杂化；反过来不管什么场景都用自由 ReAct Loop 让模型自己决定下一步，复杂多 Agent 协作场景下会失去可控性和可测试性（每个节点的输入输出边界不清楚，出错了不好定位是哪个环节的问题）。
- **解法（选型标准）**：如果任务的执行路径/分支条件在设计时就能穷举清楚（比如"先诊断、再评估风险、通过了才发布"这种固定流程），用 Graph——每个节点职责单一、可以单独测试、失败能定位到具体节点；如果任务本身需要模型动态决定下一步该调用什么、调几次（比如探索性的 SQL 数据分析），用自由 Agent Loop。
- **面试角度**：这是一个经常被问到的"什么时候用 workflow 编排、什么时候用自由 agent"的选型问题，能给出具体、可操作的判断标准（而不是"看情况"这种空话），是加分项。

## 十二、PPT 生成 / DeepResearch 的补充细节（对应路线图 Phase 6-7，技术选型演进另见第十五节 #50-57）

### 44. PPT 断点恢复的粒度是"按状态"，不是"按状态内的子步骤"
- **坑**：状态机每个状态内部可能有好几个子步骤（比如 Schema 阶段：生成 schema → 扫描图片字段 → 逐张调图片生成 API → 上传对象存储 → 回写 URL），如果在第 3 张图片生成时进程崩溃，朴素的想法是"应该从第 3 张图片继续"。
- **实际设计（不是"坑"，是一个值得讲清楚的设计取舍）**：checkpoint 只在"整个状态成功完成"时才落库（每个 strategy 是"持久化数据 + 状态推进"作为一个原子操作），所以恢复时是**整个状态重新跑一遍**（重新生成 schema、重新跑一遍全部图片生成），不是从崩溃的子步骤续。
- **面试角度**：这是"检查点粒度"的真实设计取舍——更细粒度的子步骤级 checkpoint 能减少重复工作，但要多维护一套子步骤状态机、复杂度显著上升；按状态做粗粒度 checkpoint 简单可靠，代价是重跑会有一些浪费（比如已经成功生成的图片可能被重新生成一遍，多花钱）。能讲清楚这个取舍、以及"如果要优化，会怎么加细粒度 checkpoint"，说明想清楚了工程成本和可靠性之间的平衡，不是没考虑到。

### 45. DeepResearch 的依赖上下文只做单跳，不是完整依赖图
- **坑/设计取舍**：Plan-Execute 的任务分层调度里，第 N 层任务只能看到第 N-1 层的结果，**看不到 N-2 层及更早的**——这是一个简化设计，如果真实任务需要"层层递进、后面的任务需要用到很早之前某一层的结果"这种更复杂的依赖关系，当前设计会丢失这部分上下文。
- **面试角度**：如实说这是当前设计的已知局限、不是完美方案——面试官追问"如果需要多跳依赖怎么办"时，可以谈实现思路（比如把 `accumulatedResults` 从"只存上一层"改成"存全部历史层"，或者做一个真正的任务依赖图而不是简单的 order 分层），这种"知道局限在哪、也知道怎么补"的回答比"我的设计没有问题"更有说服力。

### 46. Critique Feedback 只保留最新一条，历史的会被过滤丢弃
- **坑**：如果每一轮 Critique 的反馈意见都原样保留在消息历史里，多轮迭代之后会越堆越多，一部分是已经被后续轮次解决掉的旧反馈，继续留着只会稀释真正需要关注的最新反馈、还会占用上下文长度。
- **解法**：渲染完整上下文时，只保留最近一条 Critique Feedback，更早的历史反馈直接过滤掉不渲染（但消息本身不删除，只是渲染时跳过）。
- **面试角度**：这是"防止某一类特定内容在多轮循环里无限累积"的具体手法，和 Phase 0 的上下文压缩解决的是同一类问题（长任务的上下文膨胀），但这里用的是"针对性过滤"而不是"整体摘要"，是更轻量的局部方案——能对比出"什么时候用整体摘要、什么时候用针对性过滤"就是加分项。

## 十三、Skills 补充（来自《Agent Skills到底是如何实现的？》，对应路线图 Phase 0.7）

### 47. MiniMax maxTokens 截断导致工具调用参数变成空对象（真实生产 bug，不是设计问题）
- **坑**：让模型生成 PPTX 构建脚本这类"代码生成密集型"的技能场景下，观察到 `write_file` 工具调用偶尔出现 `arguments={}`（空参数）——第一反应很容易怀疑是"模型没理解任务"或者"工具描述没写清楚"，但真正根因是 `maxTokens: 5000` 把模型的输出（包括工具调用参数这个 JSON 本身）从中间硬生生截断了，截断后的半截 JSON 解析失败，framework 兜底成了空参数。
- **解法**：代码生成密集型场景（大段脚本作为工具参数）**去掉或调高 `maxTokens` 上限**，不能用通用场景的默认值。
- **面试角度**：这是一个"表面现象和真实根因完全对不上"的真实排查案例——症状是"工具调用参数为空/不完整"，直觉上会去查 JSON 解析逻辑、工具 schema、prompt 描述，但真正的根因在一个看起来无关的 `maxTokens` 配置项上。能讲出这个排查过程，比直接说"我们把 maxTokens 调大了"有说服力得多。

### 48. Skills 的 DB 状态与文件系统定时对账 + 请求级热加载
- **坑**：Skills 有两个数据源——文件系统（`SKILL.md` 内容的唯一真相）和数据库（`enabled`/`disabled` 状态、上传元数据）。如果只在应用启动时同步一次，运维直接往 skills 目录扔一个新文件夹（不走上传 API），这个新技能永远不会被发现，除非重启整个服务。
- **解法**：`@Scheduled` 定时任务（比如每 3 分钟）做一次文件系统↔数据库的双向对账（文件系统独有的自动插入并默认启用、数据库独有但目录已删除的判定为孤儿记录并清理、两边都有的用文件系统内容刷新描述但保留数据库里的启用状态）；同时**每次对话请求都重新从数据库读取"当前启用的技能目录"**动态构建这一次要用的 `SkillsTool`，而不是用应用启动时构建好的固定实例——这样运营人员在后台切换某个技能的启用状态，**下一轮对话立刻生效，不需要重启服务**。
- **面试角度**：这是"配置热更新"的一个具体落地方式——很多系统的"热更新"只是"改个配置文件不用重启"，这里更进一步做到"每次请求都按最新状态重新装配"，粒度更细；同时"定时对账 + 允许绕过 API 直接操作底层存储也能最终被发现"是运维友好性的一个具体设计点（不强制所有变更都走一条 API 路径）。

## 十四、文件与历史会话回放（来自《文件与联网搜索的重构》，对应路线图 Phase 0.5 / Phase 4）

### 49. 历史会话回放：附件必须知道自己属于哪一轮，但这个信息在流式开始时还不存在
- **坑**：前端要支持"点开一个历史会话，正确还原每一轮上传过哪些附件"，天然需要一个"附件属于哪一轮对话"的归属字段。但麻烦在于：**这一轮到底是第几轮、这一轮结束后会生成哪个会话记录 id，在流式请求刚发起的那一刻根本不知道**——`conversation_id` 是请求发起时就必须确定的（这样当前这一轮的 prompt 才能立刻感知到"这一轮上传了文件"），但具体这一轮落库后的行 id（比如自增主键），只有等这一轮**流式全部结束、真正写库之后**才产生。
- **解法**：用两个独立的 key，各自解决各自的问题——`conversation_id` 在流式开始的瞬间就绑定（解决"这一轮 prompt 需不需要看到刚上传的文件"这个当下问题），`session_id`（这一轮结束后落库产生的行 id）等这一轮真正跑完再回填到文件记录上（解决"以后翻历史时，这个附件对应哪一行会话记录"这个回溯问题）。且要覆盖两种收尾方式——正常走完的 `Complete` 事件、和被打断暂停的 `Paused` 事件——都要各自触发一次回填，不能只处理"正常结束"这一种情况，否则用户传了文件后又把这一轮打断，附件就变成孤儿数据，找不到自己属于哪次对话。
- **面试角度**：这是"一个字段解决不了两个不同时间点产生的需求，需要拆成两个字段各司其职"的具体案例——很多人第一反应会想"附件加个 sessionId 外键不就行了"，但会漏掉"这个 id 在需要用到它的那一刻还不存在"这个时序问题。能讲清楚这个时序矛盾以及为什么要用两个 key 而不是一个，是对"分布式/异步场景下 ID 生成时机"这类问题有真实理解的体现。

## 十五、PPT 生成的技术选型与演进（对应路线图 Phase 6，承接第十二节 #44-46）

### 50. PPT 技术路线选型：从"文生图/HTML/裸操作 PPTX"到"模板填充"
- **坑**：动手做 PPT 生成能力之前系统性试过四条路，每条都有具体翻车点：①**文生图 PPT**（nanobanana-pro 等文生图模型直接画整页）——效果惊艳但成本高（一张 4K 图大几毛到 1 块多，20 页 PPT 成本明显上升）、中文字容易"乱码/鬼画符"，更致命的是生成的 PPT 本质是图片合集，**用户打开后无法编辑文字、无法调整任何布局**；②**代码生成 PPT**（Anthropic 官方 pptx skill 路子，教模型写 python-pptx 代码）——完全可编辑，但视觉设计能力受限于代码本身，效果偏朴素；③**生成 HTML 再转 PPT**——HTML/CSS 布局体系和 PPT 底层 Office Open XML 布局体系不一致，转换时经常出现页面布局错位、字体变化、背景丢失、元素偏移；④**直接操作 PPTX（工具调用式）从零生成**——排版规划全靠模型决定每个元素的位置，很难用自然语言描述清楚精细布局，实践中布局混乱。
- **解法**：最终收敛到**模板填充**——设计交给专业设计师预先做好模板和占位符（shape name），大模型只负责生成结构化内容（JSON Schema），系统负责把内容填进模板。"设计"和"内容生成"彻底解耦，兼顾可编辑性、视觉稳定性和成本（配图甚至可以用免费的 echarts-mcp 生成图表）。
- **面试角度**：不是"拍脑袋选一个方案"，而是对四条技术路线的成本、失败模式、可维护性做了量化对比后收敛的选型决策。能讲清楚"为什么排除另外三条路"往往比直接说"我们用了模板填充"更有说服力。

### 51. PPT 信息收集阶段：SpringAI 流式+工具调用不稳定，退回自研 ReactAgent
- **坑**：SearchStrategy（信息收集阶段）本来想直接用 SpringAI 的 ChatClient 做"流式输出 + 工具调用"，但实测发现 SpringAI 在这个组合场景下"稳定性很差，有一些 bug，导致工具无法调用"。
- **解法**：绕开 SpringAI 官方的流式+工具调用组合，直接复用自研的 `SimpleReactAgent` 来做联网搜索并流式输出，收集到的最终结果再保存进 `AiPptInst`。
- **面试角度**：一个很实际的"框架能力边界踩坑"案例——遇到官方框架在特定组合场景（流式+工具调用）下的稳定性问题，没有死磕，而是用已有的自研组件绕过局限，体现对框架限制的清醒判断和快速止损能力（这也是本项目"手写 loop 优先"这条 ADR 决策在另一个真实项目里的印证）。

### 52. 需求澄清："是否继续"的判断不能靠自然语言语义解析，要靠固定标记
- **坑**：PPT 需求澄清和 DeepResearch 需求澄清都遇到过同一个问题——如果指望程序直接从模型的自然语言回复里判断"信息是否收集够了、能不能继续往下走"，会发现"程序很难准确判断模型意图"，比如模型可能说"信息已经足够，可以开始生成 PPT"，也可能说"好的，我现在帮你生成 PPT"，语义相近但没法用简单规则稳定识别。
- **解法**：在 Prompt 里强制约定专属标记——PPT 场景用【开始生成PPT】/【暂停生成PPT】，DeepResearch 场景用【需要补充信息】——流程判断只匹配这几个固定 token；同时加一层关键词兜底（命中"请问""请提供"等疑问词也判定为暂停），双保险应对模型偶尔忘记输出标记的情况。
- **面试角度**：典型的"用结构化协议约束 LLM 输出，而不是对自然语言做语义解析"的工程手法——把状态机的确定性触发条件锚定在几个固定字符串上，是控制 LLM 行为边界时非常高频的套路，能直接类比到本项目 Hooks/Governance 层"高危操作判定不能靠模型自觉"这条原则。

### 53. Schema 生成：`fontLimit` 对模型只是"软约束"，渲染侧必须暴力截断兜底
- **坑**：为了防止文本框溢出（换行异常、字体被压缩、排版错乱），系统给每个文本字段配置了 `fontLimit`（字数上限）约束模型生成内容的长度。但"大模型生成内容本身具有一定的随机性，即使设置了 fontLimit，模型生成的 content 在个别情况下仍然可能超过限制"。
- **解法**：不指望 Prompt 层约束 100% 生效，在渲染脚本里对超限文本做**暴力截断**（只替换文字不动样式，长度超了直接截）——因为生成的 PPT 本身是可编辑文件，截断带来的信息损失可以由用户手动补充调整。
- **补充（issue #30）**：这条兜底逻辑在 #24 落地时就已经写进 `render_ppt.py` 的 `apply_fill`，但当时没有测试真正验证过——`RenderStrategyTest` 补上了这个缺口：手写一个字段长度故意超过 `PptTemplateSpec` 上限的 `PptSchema`（模拟"模型没遵守 Prompt 约束"），走真实的 `RenderStrategy` → `PptPythonRenderer` 子进程 → `render_ppt.py`，再用 python-pptx 重新打开产物 pptx、读回 shape 的实际文字校验截断长度和内容，同时留一个没超限的字段做对照，证明截断是按字段各自的 `fontLimit` 精确命中，不是无差别覆盖。这也是"提示词当契约"（承接 #52/#74-76）这类失效模式里容易被漏掉的一环：代码写了兜底不代表测过兜底真的生效，没有真的构造"模型不遵守约束"这个输入去跑一遍，兜底本身也可能是"看起来对但没验证过"的假设。
- **面试角度**：很好地体现"Prompt 约束是 soft constraint，必须叠加代码层 hard constraint"这个原则——不能假设 LLM 会严格遵守数值型约束，任何有强排版/长度要求的字段都要在非 LLM 层再兜一道底（和踩坑点 #6"压缩占位符必须合法 JSON"是同一类"不能信任模型自觉遵守格式约定"的思路）。

### 54. 文生图返回的 URL 有时效性，必须转存对象存储才能持久化
- **坑**：调用文生图服务后拿到的图片 URL 一般都是有时效性的临时链接——如果直接把这个临时 URL 写进 PPT Schema 或最终 PPT 文件，等真正渲染、或者用户后续再打开这份 PPT 时，图片链接很可能已经失效，PPT 里的图直接变成裂图。
- **解法**：拿到图片 URL 后立刻下载字节流并上传到自建对象存储（MinIO），用永久地址回填 Schema 的 `url` 字段。
- **面试角度**：任何接入第三方生成式 API（文生图、文生视频、TTS 等）都会遇到的坑——不能对第三方返回的资源 URL 做"直接持久化引用"的假设，必须做一次资产固化（下载+转存自有存储），否则会在用户完全无感知的将来某个时间点批量出现"资源失效"故障。

### 55. PPT 渲染引擎选型：Java + Apache POI → Python + python-pptx
- **坑**：技术选型阶段考虑过用 Java 生态的 Apache POI 做 PPT 渲染，但实测发现"对复杂模板支持较差、图片背景处理复杂、样式容易丢失、**Group shape 支持不好**"——这对模板填充方案是致命的，因为模板填充的核心机制是靠 shape name 精确定位到最深层的原始文本框，一旦模板里存在较多组合（group）元素，POI 处理不了，就会导致填充失败或样式跑掉。
- **解法**：改用 Python + python-pptx 做真正的渲染，Java 侧只负责流程编排（状态机推进）和产物落地（结果上传对象存储），通过 `ProcessBuilder` 启动 Python 脚本、用环境变量/临时文件传递 Schema JSON，形成"Java 管流程，Python 管渲染"的异构协作架构。
- **面试角度**：一个很直接的"不迷信主语言，按任务选生态"的案例——遇到 Java 生态在某个垂直领域（复杂 Office 文档操作）能力短板明显时，果断引入更合适的技术栈，能对比脚本调用/HTTP 服务化/MCP 三种异构协作方式各自的成本取舍。

### 56. PPTX Skill 视觉效果差：官方 skill 无绘图能力 → 自研 Pillow/SVG 图片素材生成
- **坑**：直接用 Anthropic 官方 pptx skill（教 LLM 写 python-pptx 代码建 PPT）时发现，生成的 PPT 能用但"视觉效果比较朴素，都是些很单一的元素"，根因是 python-pptx 能操作的视觉元素只有基础 Shape（矩形、圆形、线条）和文本，本身没有绘图能力，做不出渐变背景、装饰图案、光晕这类丰富素材。
- **解法**：重写出两个增强版——`pillow-pptx`（LLM 写 Pillow 命令式绘图代码生成 PNG 素材再嵌入）和 `svg-pptx`（LLM 写声明式 SVG 生成矢量素材，经 cairosvg 转 PNG 再嵌入）。两者有明确取舍：Pillow 零系统依赖但 LLM 写起来繁琐（一个三色渐变要写循环逐行计算颜色值）；SVG 对 LLM 更友好（声明式、一行搞定渐变/滤镜）、生成更快、画质更高，但 Windows 上需要额外装 GTK3-Runtime/cairo 系统依赖，环境搭建成本更高。
- **面试角度**：展示了"发现开源方案效果不达预期后，如何定位根因（能力边界：无绘图能力）并针对性补足"的思路，还给出了量化对比（依赖/画质/体积/生成速度/LLM 友好度）而不是拍脑袋二选一，是很好的技术选型汇报素材。

### 57. PPTX Skill 遗留坑：多轮工具调用导致上下文膨胀、生成质量退化
- **坑**：Skills 驱动的复杂任务必然触发多轮 ReAct 循环（加载技能→分析需求→写 Python 代码→写文件→执行脚本），一轮 `write_file` 可能就塞进去几千 token 的内容，再加上 Bash 执行输出、`read_file` 返回的文件内容，上下文很快膨胀到接近模型窗口上限——模型的注意力开始分散、遗忘早期指令、对 Skill 指引的遵循度下降，最终生成质量急剧下降。
- **解法**：这正是 Phase 0 上下文压缩机制（`ContextCompactor` 两层设计）要解决的问题——不是这篇文章给出的解法，而是佐证了"为什么必须做上下文压缩"这件事的真实触发场景。
- **面试角度**：这是一个可以量化描述的"长任务上下文膨胀→质量退化"真实案例（`write_file` 单次几千 token 的具体量级），可以直接作为已有上下文压缩章节（踩坑点 #6-8）的具体触发场景佐证，让抽象的架构讲解落地到"为什么必须做上下文压缩"这个真实痛点上，而不是泛泛而谈。注意这和 #47（MiniMax maxTokens 截断导致空参数）是两个不同的坑——#47 是单次输出被截断，这里是多轮累积导致整体膨胀。

## 十六、TodoWrite 的具体动机（来自《如何让智能体自主规划》，对应路线图 Phase 0.8）

### 58. 复杂任务无显式规划，会具体表现为四类问题
- **坑**：面对"分析 2005 年 8 月员工销售业绩，给出排名、趋势、异常员工和建议"这类多步骤任务，如果任务规划只存在于模型上下文里（ReAct 默认模式），会具体表现为四类问题：**漏步骤**（查了排名，忘了趋势；写了 SQL，忘了校验结果）；**顺序乱**（还没看 schema 就写 SQL，或者还没确定口径就开始汇总）；**进度不可见**（用户只能看到工具调用，看不出整体任务完成到哪里）；**上下文变长后容易忘目标**（执行几轮工具后，最初的分析目标被上下文冲淡）。
- **解法**：引入常驻工具 `TodoWrite`，强制 Agent 在复杂任务开始前先显式列出结构化任务清单（`pending`/`in_progress`/`completed`），框架内做强校验（清单不能空、每项必须有内容、同一时间只能有一个 `in_progress`），检测到该工具存在时把任务管理规则注入 system prompt；`SKILL.md` 里也要明确写触发条件（多指标/多时间窗口/需要报告图表/预计多次 SQL 查询时必须先建清单）。
- **面试角度**：这是 Plan 模式对抗"长任务上下文遗忘"的具体落地案例，能和上下文压缩（#6-8）、Redis 任务状态管理（#30-31）放在一起讲——"更大的上下文窗口"治不了遗忘问题的根，需要把执行状态显式外部化、结构化、可校验；同一类"防止长任务失控"的问题，在不同粒度上（单轮内的任务规划 vs 跨会话的任务生命周期）用的是同一个思路：外部化 + 结构化 + 强校验。

## 十七、补遗：动态工具参数 / SubAgent / HITL 暂停恢复（来自框架 docs/core 03/18/19 与源码研读，对应路线图 Phase 0.1 / Phase 8 / Phase 1）

### 59. 系统级参数不能信任 LLM 复制，注入时还要按 schema 白名单过滤
- **坑**：两层问题。第一层：`userId`/`token`/`tenantId` 这类运行时权威值如果依赖 LLM 在工具调用参数里"抄写"，一字之差权限就错（雪花 ID 抄错一位、长 token 更不可能抄对）。第二层：框架代劳注入时，如果不加区分地把额外字段 merge 进工具参数 JSON，远程 MCP 工具（Python/Pydantic 严格校验）会直接报 `unexpected_keyword_argument` 拒绝调用——本地 `@Tool` 方法宽容地忽略未知字段，MCP 工具不会。
- **解法**：`RunnableParams` 分双通道——prompt 参数（模型可见，影响其理解）vs toolParams（永不进 prompt，在 LLM 选完工具、执行前由框架 JSON merge 强制覆盖）；merge 时先读目标工具声明的 `inputSchema.properties` 做白名单，**只注入工具真的声明过的字段**。
- **面试角度**："系统参数和业务参数的信任边界"——业务参数让模型生成，系统参数永远框架侧固化覆盖（和 #35 的跨线程固化是同一条原则的两个环节）；schema 白名单这个细节能体现"本地工具宽容 vs 远程 MCP 严格"的真实兼容性差异，是踩过才知道的坑。

### 60. SubAgent：ThreadLocal 走私上下文 + 硬性禁止嵌套
- **坑**：把子 Agent 包装成普通工具（`call_{name}`）时有三个问题：`FunctionToolCallback` 的 `Function` 接口拿不到 `ToolContext`，父 Agent 的事件流 sink 和会话参数传不进去；子 Agent 的流式事件如果直接冒到父 sink，前端分不清哪条 Thinking 是谁的；子代理再挂子代理/AskUser/暂停拦截会让上下文和暂停语义彻底混乱。
- **解法**：外层包一个能读 `ToolContext` 的 wrapper，用 ThreadLocal 在调用前 set、finally 里 clear 地把 sink/params"走私"给内层 Function；子 Agent 每个事件重新构造、打上 `SubAgentSource(agentName, subAgentId)` 标记后再转发；构建时硬校验直接拒绝嵌套（子代理工具列表里不允许出现 `call_*`/AskUser/暂停 Advisor），只允许一层。
- **面试角度**：ThreadLocal 跨接口边界传递上下文是一个"明知有代价仍然选它"的取舍（接口签名改不了时的现实解法），和 #35 里"ThreadLocal 跨线程失效"正好构成一对正反案例；"只允许一层嵌套"是主动给复杂度设上限的决策，不是能力不足。

### 61. HITL 人工审批：把"等人"从线程状态变成数据状态
- **坑**："高危操作转人工审批"如果做成同步阻塞（线程停在那等人点头），线程被长时间占住，服务一重启审批现场就全丢了；而且"审批暂停"和"用户主动中断"是两种语义，混在一起处理会乱（恢复时该不该执行挂起的工具？答案不一样）。
- **解法**：拦截器识别到需审批的工具调用后**不执行**，把现场打包成 `PauseState` 快照（消息列表副本 + pendingToolCalls + 当前 SafePoint 阶段 + PauseReason），持久化后发 `Paused` 事件、正常结束流——线程立刻释放。外部审批完成后 `resumeStream` 按 `PauseReason` 分支：HITL 审批通过→补执行挂起的工具再继续循环；用户中断且带了新指令→跳过挂起工具、注入新 UserMessage。`SafePoint` 是单向状态机并标注风险等级（INIT 无副作用 / LLM_STREAMING 只有 token 成本 / TOOL_EXECUTION 工具可能已部分执行——衔接 #34 的幂等性边界）。另一个细节：快照持久化失败只记日志、**不阻塞 Paused 事件发出**——内存里的暂停永远成功，持久化是尽力而为。
- **面试角度**：这是 workflow 引擎"把等待外部输入从线程状态转为数据状态"的核心思想在 Agent 里的落地——能把这个类比讲出来，说明理解的是模式而不是某个框架的 API；两种 PauseReason 的恢复分支差异是容易被追问的细节。

## 十八、Reactor 流式工程补遗（对应路线图 Phase 0.10，Java 并发主线核心素材）

### 62. 工具并发执行和流式聚合不能共用 boundedElastic
- **坑**：`Schedulers.boundedElastic()` 默认上限 10×CPU 线程。工具并发执行（`ToolCallExecutor`）和流式聚合/重试调度如果都扔进这一个池，高并发下互相抢线程——慢工具把池占满时，别的会话连流式聚合都调度不动。
- **解法**：拆独立池（`Schedulers.fromExecutor` 包自建线程池），工具执行一个池、loop 调度一个池，池参数各自按负载特征定。
- **Java 角度**：线程池隔离（舱壁模式）的经典应用；能讲出 boundedElastic 的默认参数和"为什么共池会互相拖死"，比背"线程池七参数"有说服力。

### 63. 会话持久化必须在 tryEmitComplete 之前，不能放 doFinally（agentx 源码里的真实教训）
- **坑**：把"保存会话历史"放在 `doFinally` 里看起来很自然（流结束时清理），但 `doFinally` 的执行时机在终止信号**之后**——下游收到 Complete 就认为一轮结束了，此时若 JVM 退出（部署重启、容器被杀），doFinally 里的入库还没跑完，历史直接丢失。agentx 源码里有多处注释明确记录这个教训："在 tryEmitComplete() 之前执行，避免 doFinally 时序问题导致 JVM 退出时数据丢失"。
- **解法**：持久化作为发出 Complete 事件**之前**的同步步骤（我们的 `emitCompleteAndCleanup` 已经是这个顺序——持久化 → emit Complete → tryEmitComplete → removeTask），`doFinally` 只做真正的资源清理（stopTask 等幂等操作）。
- **Java 角度**：Reactor 终止信号与副作用操作符的时序语义（`doOnComplete` vs `doFinally` 的区别）是响应式编程的高频追问点，这里有真实事故背书。

### 64. 无界背压 buffer 与一刀切超时
- **坑**：`Sinks.many().unicast().onBackpressureBuffer()` 的 buffer 默认无上限——"模型长输出 + 前端慢消费"（比如用户切后台，SSE 消费停滞）场景下 buffer 持续膨胀，OOM 风险。超时同理：thinking 模型首 token 可能要几十秒，后续 token 间隔却是毫秒级，一个统一的 `timeout` 要么误杀首 token 等待、要么对中途卡死不敏感。
- **解法**：buffer 有界化（带容量参数的 `onBackpressureBuffer` 或 `limitRate`），溢出策略明确（丢弃旧事件/断流报错）；超时拆成 TTFT 超时和 token 间隔超时两个不同阈值；`timeout` 只断下游，要配合 `cancel()` 真正释放上游模型调用。
- **Java 角度**：背压是 Reactive Streams 的核心概念，能从"一个具体的 OOM 场景"讲到"buffer/drop/latest/error 四种溢出策略怎么选"，是最能区分"用过 Reactor"和"理解 Reactor"的话题。

## 十九、另一类代码走查案例（含"注释与代码不符"类真实缺陷——反例和正例一样值钱）

### 65. 分布式锁切面把 Throwable 包成受检 Exception，@Transactional 静默不回滚
- **坑**：另一个项目里见过的 `@DistributeLock` 切面设计正确（`@Order(Integer.MIN_VALUE)` 保证锁在事务外、SpEL 解析锁 key、`isHeldByCurrentThread()` 守卫 unlock），但有一处致命细节：`catch (Throwable e) { throw new Exception(e); }` 把业务运行时异常统一包成了**受检 Exception**——而 Spring `@Transactional` 默认只对 `RuntimeException`/`Error` 回滚。加了锁的 `split()` 方法一旦内部抛异常，事务**不会回滚**，数据处于中间态。
- **解法**：切面透传原始异常（或至少保留 RuntimeException 不包装）；或事务注解显式 `rollbackFor = Exception.class`。
- **Java 角度**：一条线串起三个高频八股——AOP 切面顺序（为什么锁必须在事务外）、Spring 事务回滚规则（受检 vs 非受检）、异常包装的破坏性。这是"从真实代码里挑出 bug"级别的面试素材，比正确案例更稀缺。

### 66. @Async 监听器读到未提交的事务数据（源码注释里写明的教训）
- **坑**：事件驱动流水线里，`split()` 在事务内发布事件，监听器如果用普通 `@EventListener` + `@Async`——异步线程立刻执行，此时 `split()` 的事务还没提交，监听器从数据库读到的状态还是旧值，后续判断直接走错分支。该项目源码注释完整记录了这个坑。
- **解法**：`@TransactionalEventListener(phase = AFTER_COMMIT)`——事件处理延迟到事务提交之后。配套：异步线程池显式配置（core 4/max 8/queue 50/`CallerRunsPolicy`）+ 优雅停机等待。
- **Java 角度**：事务可见性 + 事件机制 + 线程池配置三合一；`@TransactionalEventListener` 四个 phase 的区别是必然的追问。

### 67. 空值缓存无 TTL + "穿透/击穿"术语混用 + README 与代码不符
- **坑**：另一个项目的缓存层有三个真实问题：①空值缓存（防穿透）没设过期时间——一旦数据后续真的写入，这个"永久空值"会一直挡住正确数据；②源码注释把"缓存空值防穿透"写成"防击穿"（击穿是热点 key 过期后并发打库，需要互斥重建，代码里根本没做）；③README 宣称"HashMap→Redis→MySQL 三级缓存"，实际代码只有两级，所谓 L1 只是单次检索内的方法局部变量。
- **解法**：空值缓存必须带短 TTL；术语按定义用（穿透=查不存在的 key，击穿=热点 key 过期瞬间，雪崩=大批 key 同时过期）；文档和代码定期对账。
- **Java 角度**：缓存三大问题的准确区分是基础八股，但"我在真实项目里见过把穿透写成击穿、见过无 TTL 空值缓存"这个讲法立刻把背诵变成了经验。

### 68. 补偿任务声明了重试上限和延迟窗口常量，但根本没用上
- **坑**：另一个项目的补偿 Job 用"状态位扫描"找卡在中间态的记录重放（这个思路本身对），但 `MAX_RETRY_COUNT=5` 和 `COMPENSATION_THRESHOLD_MINUTES=5` 两个常量声明了却没有任何存活代码引用——实际效果：没有重试上限（坏数据永远重试）、没有延迟窗口（可能和正在执行的正常流程抢同一条记录重复处理）。
- **解法**：补偿必须有三要素——延迟窗口（只补"卡了超过 N 分钟"的）、重试上限（超限转人工/死信）、幂等保证（和正常流程用同一把分布式锁）。
- **Java 角度**：定时补偿是最终一致性的标配方案，但"补偿和正常流程赛跑"这个坑很少有人讲得出来；顺带引出 Outbox/本地消息表 vs 状态位扫描的对比。

### 69. prototype bean 自注册白名单在多节点部署下失效（源码注释里的集群教训）
- **坑**：Agent 注册表如果靠"prototype bean 首次实例化时自注册"维护运行时白名单，多节点部署下会话漂移到一个**从未实例化过该 Agent** 的节点时，白名单查不到、跨节点恢复直接失败。该项目源码注释明确记录了这个教训，最终方案是放弃自维护 Map、完全委托 Spring 容器（beanName 约定推导 + `getBean` 运行时查找）。
- **解法**：分布式场景下"本地注册表"天然不可信——要么用约定（beanName 推导）让每个节点都能独立解析，要么把注册表放共享存储。
- **Java 角度**：Spring bean scope（prototype 保证会话隔离）+ "本地状态在集群下失效"这个通用模式（和 #30 的 Redis 锁、#48 的 Skills 对账是同一主题的三个变奏）。

### 70. 快路径优化引入"影子历史"断裂（一个教科书级案例）
- **坑**：意图识别加了 L1 规则/L2 向量快路径（命中就跳过问题改写 Agent，省一次 LLM 调用）——优化本身对，但副作用是：被跳过的改写 Agent 本轮没有产生会话历史，下一轮如果走慢路径，改写 Agent 看不到上文、无法做指代消解（"它的第三部分"不知道"它"是谁）。
- **解法**：快路径命中时手工合成一对 user/assistant 消息（assistant 内容按改写 Agent 的输出契约构造 JSON）写回会话——"影子历史"补偿。
- **面试角度**："每个优化都有隐藏成本"的完美论据——加快路径 → 状态断裂 → 需要补偿写入，三步完整闭环，比空谈"优化要考虑副作用"具体得多。

### 71. 手写熔断器：降级方式是"从工具列表里移除"而不是"拦截调用"（一个真实亮点）
- **亮点**：Tool 粒度熔断，CLOSED→OPEN→HALF_OPEN 三态，Redis 存状态（多实例共享熔断视图）+ 两段 Lua 脚本保证复合操作原子性（INCR+EXPIRE 合一，避免两次往返间失败留下无 TTL 脏 key）；指数退避冷却派生计算不持久化。最特别的设计：熔断后**把工具从 Toolkit 里物理移除**——LLM 下一轮根本看不到这个工具，从源头杜绝再次调用，而不是等 LLM 调了再拦截报错（后者会浪费一轮推理）。
- **附带的真实缺陷**：注释说失败判定看 `[ERROR]` 前缀，代码实际是 `contains("Tool execution failed")`——注释漂移 + contains 有误判风险（工具正常返回文本里包含这个串就会被误判失败）。
- **面试角度**：熔断三态 + Redis Lua 原子性 + "对 LLM 的降级要作用在它的可见性上而不是调用路径上"（这是 Agent 特有的洞察，传统微服务熔断没有这个维度）。

### 72. 硬编码密钥的三重放大（根 pom 反面教材）
- **坑**：根 pom `<properties>` 里明文写着 dashscope API Key。三个放大因素：①父 POM 属性被全部 17 个子模块继承，爆炸半径全仓库；②同一 pom 开了 `<filtering>true`，key 会在构建时注入 resources 打进 jar——构建产物也带密钥；③测试代码里还有第二个不同的硬编码 key。且都已进 git 历史——`git rm` 无效，必须吊销轮换。
- **解法**：环境变量/配置中心/Vault 外部化；CI 加 secret scanning（gitleaks）；已泄露的 key 一律轮换。
- **面试角度**：可以主动讲"我参考的项目就这么干的，我怎么改造"——把别人的反面教材变成自己的加分项；Maven resource filtering 会把属性打进产物这个细节大多数人不知道。

### 73. 虚拟线程：适合"发后不管的旁路任务"，不是万能池替代品（真实项目实测）
- **坑**：另一个项目里三处用 `Thread.ofVirtual()`/`Thread.startVirtualThread()`（异步生成会话标题、查询改写、清理临时文件），但都是裸起——**没有背压、没有失败重试、没有结果追踪**，标题生成失败只落一条 warn 日志，调用方永远不知道。虚拟线程"创建成本低到可以随便 new"这个特性反而放大了这个问题：如果不做限流，出问题现场的虚拟线程数量会比传统线程池场景更难排查（没有池、没有队列长度这些天然的观测点）。
- **解法**：虚拟线程适合替代的是"IO 密集、阻塞、不需要池化复用"的旁路任务（这里的标题生成完全符合），但仍然需要显式的结果追踪（哪怕只是记一个 Future 或往 DB 写个状态位）和限流（`Semaphore` 或 `StructuredTaskScope` 管理生命周期），不能因为"创建便宜"就跳过这些。
- **Java 角度**：Java 21 虚拟线程是必考新特性，标准答案止步于"轻量级、由 JDK 调度、适合 IO 密集"，但能补一句"虚拟线程削弱了传统线程池的背压/观测能力，用的时候要自己补回来（限流+结果追踪），我在真实代码里见过反例"——这是从"知道特性"到"知道边界"的分水岭。

## 十九点五、"提示词当契约"的失效模式（承接 #52，代码审查角度的补充）

对 #52 的"固定标记 + 关键词兜底"设计做代码审查后发现的几类共性问题：某类规则只写在 Prompt 文本里约束模型行为，但代码侧既没有校验也没有兜底，模型一旦不遵守，后果直接从"体验变差"升级成"状态机走错分支/数据泄露/程序崩溃"。这几类要在 Governance 层（Hooks/#3 治理层）设计时一并当成设计输入，不是留到测试阶段才发现。

### 74. 状态机跳转判定的默认值必须 fail-closed，不能 fail-open
- **坑**：#52 的固定标记 + 关键词兜底方案里，如果模型的回复既没命中固定标记、也没命中兜底关键词（措辞恰好绕开了两层判断），这类"双保险都没兜住"的情况需要一个默认值——如果默认值是"继续"（fail-open），系统会把一个实际上不确定的模型输出当成"确认可以继续"处理，进而触发下游可能代价不小的操作（真正开始渲染、真正开始执行长流程）。
- **解法**：触发昂贵/不可逆操作的状态机分支，判定不明确时默认必须是"暂停等确认"（fail-closed），不能默认"继续"；同时把"两层判断都没命中"本身当成一个需要被观测到的信号（打日志/计数器），而不是静默吞掉走默认分支。
- **面试角度**：和 Hooks/PreToolUse 拦截高危操作是同一个原则的两种体现——"不确定就別做"永远比"不确定就先做"更安全，这条原则贯穿状态机判定和工具调用审批两个层面。

### 75. "禁止重复调用同一工具"这类规则需要代码侧去重，不能只写在 Prompt 里
- **坑**：常见的 Prompt 约束"不允许重复调用同一个工具（名称+参数完全一致），除非失败"，如果只写在 system prompt 里、执行工具调用的代码没有对应的去重检查，模型不遵守时唯一的兜底是 `maxRounds` 轮次上限——最坏情况不是死循环失控，而是悄悄浪费 N 轮工具调用直到撞上轮次上限，运行时既不报错也不好排查。
- **解法**：在 `ToolCallExecutor`（或等价的工具执行层）维护本轮/本次会话的"已调用工具签名"集合（工具名+参数摘要），命中重复时可以选择直接短路返回缓存结果、或提前发出警告日志，而不是放任模型再跑一轮浪费的推理。
- **面试角度**：和 #2"参数校验失败降级"是同一类"框架层要对模型的不确定行为兜底"，但这条更隐蔽——它不会报错，只会悄悄浪费成本，属于"没有异常但有问题"的一类 bug，排查成本反而更高。

### 76. 涉及内部标识符/长度上限的 Prompt 约束，输出侧要有代码强制，不能只靠模型自觉
- **坑**：两类常见但容易被忽视的 Prompt 约束：①"禁止在回答中透露内部 ID（fileId 等）"——这类数据泄露防护如果只写在 Prompt 里，SSE 输出流没有任何正则扫描/脱敏兜底，模型一旦在某次回答里不小心带出内部标识符，没有任何机制能拦下来；②"压缩输出的字符数不得超过 XX，这是硬性上限"——这类约束如果代码侧拿到压缩结果后不做长度校验就直接使用，模型没遵守时下游会继续把"应该已经压缩过"的超限内容当成合法输入处理。
- **解法**：①在响应流的输出侧加一层与模型无关的正则/规则扫描，命中内部标识符格式就脱敏替换，作为独立于 Prompt 约束的第二道防线；②"硬性上限"类约束必须在拿到模型输出后用代码校验实际长度，超限走确定性截断兜底，不能假设模型输出已经满足约束。
- **面试角度**：把这条和 #40/#41 MCP Server 对外暴露的安全线放在一起讲，能串成一条"AI 系统里，凡是关系到安全边界或硬性约束的规则，绝不能只靠模型自觉遵守 Prompt 指令，必须有一层不依赖模型行为的代码强制"——这是 AI 应用安全设计里最容易被低估、也最值得主动讲的一条原则。

### 77. Redisson 分布式锁 AOP 化的两个真实缺陷：固定 TTL 无续期 + 同步 unlock 假设遇上响应式方法
- **坑**：#65 挑过同一个 `@DistributeLock` 切面的"受检异常吞掉回滚"缺陷，这里是同一份切面源码里另外两个更隐蔽的问题，和本项目 `AgentTaskManager`/`RedisTaskLock`（issue #11）直接相关：①切面用 Redisson 的 `RLock`，调用方通过注解显式传一个固定 `expireTime`——只要传了这个参数，Redisson 自带的锁续期看门狗（不指定 leaseTime 时才会自动介入）就不会生效，锁纯粹靠这个固定 TTL 到期，没有任何东西替它续期。如果被保护的操作实际跑得比这个 TTL 还久（比如一次可能持续很久的 Agent 会话），锁会在操作还在真实进行时就过期，被另一个实例抢到手，两个实例同时处理同一份状态。②`finally` 块里 `if (rLock.isHeldByCurrentThread()) { rLock.unlock(); }` 隐含"`pjp.proceed()` 返回时，被保护的操作已经跑完了"——这个假设只对同步方法成立。如果 AOP 包裹的方法返回的是 `Flux`/`Mono`（响应式代码里很常见），方法几乎立刻就返回了（只是订阅上了，真正的异步工作这时候才刚开始），`finally` 里的 `unlock()` 会在真正的工作还在跑的时候就把锁放了——保护形同虚设。
- **解法**：①锁的生命周期管理不能靠"设一个够长的固定 TTL 然后祈祷"——要么用 Redisson 默认的 watchdog（不显式传 leaseTime，代价是不能精确控制过期时间），要么自己起一个调度器周期性对当前持有的锁做"校验归属 + 续期"（必须是一次原子操作，Lua 脚本或 Redisson 原生 API，参见 #30，不能拆成两条命令）。②给"返回值是 `Flux`/`Mono` 的响应式方法"加锁时，声明式的"AOP 环绕通知 + 方法返回即释放"这套模式直接不成立，正确做法是不用注解+AOP，在真正对应异步生命周期的节点上手动、显式地加锁/解锁——锁应该在"任务登记"时获取，在"任务真正完成"（不是"发起调用的那个方法返回"）时释放，这正是 `AgentTaskManager.registerTask`/`stopTask`/`removeTask` 这几个方法存在的意义，而不是把加锁做成一个装饰性的注解。
- **Java/分布式角度**：这条把两个经常被分开讨论的话题接在一起——"分布式锁续期的正确性"（Redisson watchdog 原理、TTL vs 心跳的取舍，呼应 #30/#31）和"响应式编程里方法返回值不代表工作完成"这个更基础的 Reactor 心智模型问题。很多人知道"锁要续期"，但不知道"声明式 AOP 加锁在响应式代码里天然不可靠"这一层；能同时讲清楚这两点，说明真正理解了"锁保护的是状态的生命周期，不是一次方法调用的生命周期"这个本质区别。

### 78. 真实流式 ChatModel + 工具调用组合，才会暴露"响应式链里藏了一个同步 block()"
- **坑**：`ToolCallExecutor.execute()` 把并发工具调用 `subscribeOn` 到独立调度器后，最外层用 `.block()` 收敛结果——这行代码本身没错，错在**调用它的线程是谁**。`AgentLoopExecutor.scheduleRound()` 订阅 `llmInvoker.streamRound(...)` 时没有主动切换调度器，`doOnComplete(() -> finishRound(...))` 就在**上游 Flux 的信号线程**上执行；如果上游是真实的 Reactor Netty 实现（`OpenAiChatModel` 走 `openai-java` SDK + Netty），信号线程就是 `reactor-http-nio-*`——Reactor 显式禁止在这类"不可阻塞"线程上调 `.block()`，命中就是 `IllegalStateException: block()/blockFirst()/blockLast() are blocking, which is not supported in thread reactor-http-nio-N`。这个 bug 在本项目里潜伏了整整一个 Phase（issue #17-#28 全部用 `ScriptedChatModel`——一个直接 `Flux.fromIterable` 返回、根本不会调度到 Netty 线程的测试替身），直到 issue #22 第一次把"真实 HTTP 流式模型"和"真实工具调用"同时接在一起跑集成测试才炸出来。
- **解法**：在 `llmInvoker.streamRound(...)` 之后、`doOnNext`/`doOnComplete` 之前插一次 `.publishOn(Schedulers.boundedElastic())`，把后续所有下游操作符（包括会触发 `finishRound` → `ToolCallExecutor.execute()` → `.block()` 的那条路径）都搬到允许阻塞的调度器上执行。`subscribeOn` 管的是"upstream 源头在哪个线程订阅"，`publishOn` 管的是"downstream 操作符在哪个线程执行"——这里要控制的是后者，两个操作符职责不同，选错了不会报错，只会在真正对接真实网络实现时才失效。
- **Java/Reactor 角度**：这条和 #62/#63/#64 一起构成"响应式编程线程模型"的完整案例集，但这条最典型地展示了"测试替身跑得通不代表生产实现跑得通"——`ScriptedChatModel` 在这里不是"简化了业务逻辑"，而是**悄悄抹掉了一个只有真实 I/O 实现才会暴露的调度器语义**。面试可以直接点破：Mock/Stub 测试替身的选型，不能只看"返回值对不对"，还要看它有没有忠实复现被替换对象的**执行模型**（同步 vs 异步、哪个线程发信号）——这正是很多"单测全绿、联调必炸"的根因。

### 78a.（同一次排查的次要发现，未在本项目内修复）Spring AI 2.0 `OpenAiChatModel` 合并流式 tool_call chunk 时对 DashScope 不完全兼容
- **现象**：接 `qwen-plus`（DashScope OpenAI 兼容模式）时，一旦某一轮触发工具调用，`OpenAiChatModel$ChunkMerger.chunkToChatCompletion` 内部一个 `Optional.get()` 会抛 `NoSuchElementException: No value present`；同样的调用链换成 `deepseek-chat` 完全正常。定位到是 `spring-ai-openai:2.0.0` 合并 tool_call 分片 chunk 时，假设了某个字段（很可能是分片延续 chunk 上的 `id`/`index`）一定存在，而 DashScope 的流式分片形状和 OpenAI 官方在这个细节上不完全一致。
- **处置**：这是第三方库（`spring-ai-openai`）内部实现的兼容性问题，不是本项目代码可以修的范围；暂时的规避方式是"挂了 Web 搜索这类工具的对话默认路由到 `deepseek-chat`，`qwen-plus` 保留给纯对话场景"。真要修，路径是升级 `spring-ai` 版本看是否已修复，或向上游报告这个兼容性 bug。
- **面试角度**：和 #78 放在一起讲是一条完整的"真实联调排查"叙事——同一次真机测试里连续挖出两个平时被 Mock 掩盖的问题，一个是自己代码的线程模型 bug（能修、已修），一个是第三方库的厂商兼容性 bug（不能改源码、只能规避+报告）。能清楚区分"这个坑归谁修"本身就是排查能力的一部分。

### 79. 构造函数里字段初始化顺序反了：懒加载的变体测得出来，急加载的变体测不出来
- **坑**：issue #23 给 `AgentLoopExecutorFactory` 加图表工具支持时，构造函数被重新整理成"先把 `plainExecutorsByModelId`（每个注册模型各建一个不挂搜索/图表工具的执行器）建好，再把 `this.taskManager`/`this.webSearchToolProvider`/`this.chartToolProvider` 这几个字段赋值"。问题是 `plainExecutorsByModelId` 的初始化调的是 `buildExecutor()`，这个私有方法读的是**字段** `this.taskManager`，不是构造函数参数——Java 对象字段在显式赋值之前默认值是 `null`，构造函数体内的语句是按书写顺序执行的，不是"先把所有字段都定下来再跑方法体"。于是每一个非懒加载的 `plainExecutorsByModelId` 执行器，实际上都是拿着一个还没赋值（`null`）的 `taskManager` 建出来的。同一个类里另外两个变体——`forModel(id, true)` 懒加载的搜索执行器、`forModelWithCharts(...)` 懒加载的图表执行器——因为 `buildExecutor()` 调用发生在构造函数**返回之后**的某次真实请求里，这时候 `this.taskManager` 早就赋值完了，完全不受影响。结果是：全部走懒加载路径的单元测试（`AgentLoopExecutorFactoryTest` 里搜索/图表相关的用例）全绿，只有 `DeepResearchService`（用的是构造阶段就建好的 `plainExecutorsByModelId`）在接真实流式模型时，第一次真实调用触发 `AgentTaskManager.registerTask(...)` 就 `NullPointerException`——而且这个 NPE 第一次出现时，恰好和另外两个并发子 agent 正在同一个工作树里改这份文件重叠，一度被误判成"并发编辑导致的环境噪音"而不是真 bug，多跑了几次集成测试才确认是真的、和并发编辑无关。
- **解法**：构造函数里，任何"字段初始化表达式依赖另一个字段的值"的写法，必须严格保证依赖的字段先赋值——这里就是把 `this.taskManager = taskManager;`（以及它引用到的 `webSearchToolProvider`/`chartToolProvider`）挪到 `plainExecutorsByModelId` 的初始化语句之前。更通用的教训：一个类里如果同时存在"构造阶段就建好"和"请求时才懒加载"两种初始化路径，构造阶段这条路径对字段赋值顺序的敏感度远高于看起来的样子——因为它是在 `this` 还没完全"活起来"的时候执行的，而懒加载路径是在对象已经完全构造完成之后才第一次运行，天然不会踩到这类顺序问题，这也是为什么这类 bug 精确地只影响"急加载"的那个变体，是排查时判断"该往哪个方向找"的一个有效线索。
- **Java 角度**：这是"Java 对象初始化顺序"这个八股题目里经常被简化成"父类先于子类、字段先于构造函数体"的规则,在**同一个构造函数内部**的具体表现——很多人背得出"字段初始化器和实例初始化块按声明顺序在构造函数体之前执行"，但构造函数体本身内部的多条语句同样是严格按书写顺序执行、彼此之间没有"先决算所有字段"这回事，一旦某条语句的副作用（这里是调用一个读取 `this.xxx` 的私有方法）被安排在依赖字段赋值之前，编译器不会报错，因为语法上完全合法——这类 bug 只能在运行时、且只在真正触达那条代码路径时才会现形，是"能编译 ≠ 能跑对"的一个具体例子，也是为什么"仅用同步/合成测试替身跑通的单测"不能代表"接真实实现也跑得通"（和 #78 是同一类"测试替身掩盖了真实执行路径"的教训，但这次坑在对象构造阶段而不是响应式调度阶段）。
