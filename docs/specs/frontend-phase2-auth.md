# AgentTrail 前端工程 — Phase 2（登录/权限 + SQL 数据分析）需求 Spec

> 状态：草案，按 `to-spec` 模板整理，尚未发布为 GitHub issue（`renjian-pro/AgentTrail`，`ready-for-agent` 标签）——v1 已拆票（[#38-#43](https://github.com/renjian-pro/AgentTrail/issues/38)），这份先搁置，等 Phase 2 后端启动时机更明确了再拆。与 [`frontend-v1.md`](frontend-v1.md)（v1：对话/文件问答/DeepResearch/PPT）是同一个前端应用的后续增量，不是另起一个项目。

## Problem Statement

`docs/roadmap.md` Phase 2 已经规划了一套企业级的数据权限模型（部门树 + 角色 + DataScope 分级 + AST 改写 + 敏感字段脱敏），这是本项目区别于"随便接一个 Text-to-SQL demo"的核心卖点之一。但这类机制天生"看不见摸不着"——不接前端，面试官/评估者没法直观看到"同一句自然语言问题，不同角色的人问出来结果不一样"这个效果，权限模型做得再精细也只能靠读代码验证。

同时，SQL 数据分析这类对话和 v1 spec 里的通用对话不完全一样：需要展示 schema 探查过程、SQL 校验结果、结构化表格、图表，这些是 v1 对话 UI 没有覆盖的渲染需求。

## Solution

在 v1 前端（同一个 Vue3 + TS + Vite 应用，不另起项目）基础上新增两块：

1. **登录 / 用户 / 角色 / 部门管理**：登录页、鉴权路由守卫、用户管理（列表+搜索+分页+新增/编辑+启停+删除）、部门树选择组件、当前用户信息展示
2. **SQL 数据分析对话渲染扩展**：复用 v1 spec 已经设计的流式事件体系，新增对 schema 探查、SQL 校验、执行结果表格、图表图片、脱敏字段提示这几类工具调用结果的专属渲染

参考实现里验证过的模式（登录鉴权、DataScope 分级选人、脱敏遮罩、把权限状态显式讲给用户看）作为设计起点，不照搬代码，独立实现。

## User Stories

### 登录 / 身份

1. 作为访问者，我想通过用户名密码登录，以便进入需要身份的功能区
2. 作为访问者，我想在登录失败时看到明确的错误提示（账号密码错误 / 账号被禁用），以便理解失败原因
3. 作为已登录用户，我想在页面刷新后仍保持登录态，以便不用每次都重新登录
4. 作为已登录用户，我想主动登出，以便切换身份对比不同角色的可见范围
5. 作为已登录用户，我想在顶栏看到自己当前的身份信息（用户名/角色/部门），以便确认自己是以什么身份在操作
6. 作为演示访问者，我想用预置的几个不同角色/部门的演示账号登录，以便对比展示数据权限过滤的效果
7. 作为未登录访问者，访问需要鉴权的页面时我想被自动跳转回登录页，以便理解需要先登录

### 用户 / 角色 / 部门管理

8. 作为管理员，我想看到分页的用户列表并支持按用户名/昵称搜索，以便管理大量用户
9. 作为管理员，我想新增用户并为其分配角色（多选）和部门（多选，树形），以便控制新用户的初始权限范围
10. 作为管理员，我想编辑已有用户的角色/部门分配，以便调整权限范围
11. 作为管理员，我想启用/禁用某个用户，以便临时收回访问权限而不必删除账号
12. 作为管理员，我想删除用户，以便清理不再需要的账号；系统应阻止我删光所有 admin（后端保证，前端只需正确展示这类校验错误）
13. 作为管理员，我想在表单里看到部门树结构并勾选，以便理解组织架构如何映射到数据权限
14. 作为管理员，我想查看角色列表及其对应的数据范围（ALL/DEPT_AND_SUB/DEPT/SELF），以便理解每个角色实际能看到什么数据

### SQL 数据分析对话

15. 作为分析用户，我想用自然语言提问业务数据问题，并看到 agent 探查表结构（schema）的过程，以便理解它是怎么找到相关表的
16. 作为分析用户，我想看到 agent 生成并校验 SQL 的过程（而不只是最终结果），以便验证 SQL 安全校验机制真的在生效
17. 作为分析用户，我想看到 SQL 执行结果以表格形式清晰展示，以便阅读结构化数据而不是一堆文字
18. 作为分析用户，我想在需要可视化时看到生成的图表，以便直观理解数据趋势/分布
19. 作为分析用户，当结果中包含敏感字段（如身份证号）时，我想看到明确打码的值和"该字段已脱敏"的提示，以便理解这不是数据缺失而是策略生效
20. 作为分析用户，当我的问题超出我的数据权限范围时，我想看到清晰的提示（而不是报错或空结果），以便理解是权限问题而不是系统故障
21. 作为演示访问者，我想切换到数据范围更窄的账号重新问同一个问题并看到结果自动收窄，以便直观验证权限模型真的按用户改写了查询
22. 作为分析用户，我想在提出有歧义的业务术语（如"销量"对应多个字段）时看到 agent 消歧的过程或反问，以便理解术语词典机制
23. 作为分析用户，我想在涉及复杂计算的问题里看到 agent 调用专门的计算工具而不是直接输出模型自己算的数字，以便验证"不让 LLM 自己算"的设计

### 跨模块 / 工程

24. 作为前端维护者，我想登录态在 API client 层统一处理（自动带认证头、401 自动跳转登录），以便每个业务组件不用重复写鉴权逻辑
25. 作为前端维护者，我想 SQL 分析对话复用 v1 spec 已经设计的流式事件类型体系（`ToolStart`/`ToolEnd`/`Text`/…），只新增 SQL 场景专属的展示组件，以便不用重新设计一套对话渲染框架
26. 作为前端维护者，我想部门树组件做成可复用组件（勾选/展开逻辑独立），以便用户表单和其他可能用到部门选择的地方共享同一份实现

## Implementation Decisions

### 整体定位

复用 v1 spec 的技术栈（Vue3 + TS + Vite）、路由结构、API client 分层和流式事件类型体系，不新起一个应用；这份 spec 只新增模块和路由。

### 新增模块

| 模块 | 组件 | 说明 |
|---|---|---|
| 登录 | `LoginView` | 用户名密码表单，登录成功后保存登录态标记，跳转回原本想访问的页面（`redirect` query 参数） |
| 鉴权 | `AuthGuard`（路由守卫）+ API client 拦截器 | 未登录访问受保护路由跳登录页；任意请求收到 401 全局跳登录页并清空本地登录态 |
| 用户管理 | `UserManagementView`、`UserFormDialog`、`DeptTree`（可复用组件） | 表格 + 搜索 + 分页 + 新增/编辑弹窗（角色多选 + 部门树多选）+ 启停 + 删除确认 |
| 角色查看 | `RoleListView` | 是否做成可管理页面取决于 Phase 2 后端角色是否开放 CRUD（见 Out of Scope），先按只读列表设计 |
| 顶栏身份展示 | `UserBadge` | 展示当前用户名 + 角色 + 部门，点击登出 |
| SQL 分析对话渲染扩展 | 在 v1 已有 `ToolTimeline` 组件基础上新增分支 | 针对 `listTables`/`describeTables`/`validateSql`/`executeSql`/`calculate`/`generate_chart` 这几类工具调用做专属渲染：schema 卡片、SQL 语句高亮块、结果表格、图表图片（`<img>`，不接入前端 ECharts 做交互式图表）、脱敏字段徽标 |

### 权限/脱敏的展示原则

权限状态、脱敏提示这些"解释性文案"完全由后端返回内容驱动（对应参考实现里"把权限状态显式讲给用户/模型听"的思路），前端不在本地维护一份权限规则副本去自己判断"这个字段该不该脱敏"——脱敏与否、数据范围收窄与否，都是后端算好之后前端照原样渲染。

## Testing Decisions

- `LoginView`/`AuthGuard`：mock 登录成功、登录失败、401 全局拦截跳转三条路径
- `DeptTree`：勾选/展开的组件测试，覆盖多级嵌套场景
- SQL 结果渲染组件：用固定 fixture（模拟 `executeSql` 返回的表格 JSON、标了脱敏标记的字段）测试渲染正确性，不依赖真实数据库/真实后端
- 不测"是否真的按角色过滤对了"这类后端权限逻辑——那是后端 `DataScopeRewriter` 自己的测试范围（Phase 2 后端票的事），前端测试只负责验证"如实渲染了后端返回的内容"

## Out of Scope

- 角色的新增/编辑/删除：如果 Phase 2 后端角色是预置种子数据、不开放动态角色管理接口，这里就不做；待后端那张票明确接口范围后再定，`RoleListView` 先按只读设计留好扩展空间
- 部门树结构本身的新增/编辑/删除：先只支持"选择已有部门"挂在用户身上，管理部门树结构可能不在这一期前端范围内
- 忘记密码 / 找回密码 / 自助注册：demo 项目账号由管理员预置，不需要自助流程
- 按钮级细粒度权限控制（谁能点哪个具体按钮）：只做"未登录整体拦截"和"数据范围过滤"两个粒度
- 移动端适配

## Further Notes

- **依赖 Phase 2 后端优先交付**：`sys_user`/`sys_role`/`sys_dept` 建表 + 登录接口 + `DataScopeResolver`/`DataScopeRewriter` + 敏感字段脱敏 + SQL 分析工具（`listTables`/`describeTables`/`validateSql`/`executeSql`/`calculate`/`generate_chart`）——这些目前一行代码都没有，建议单独开一张后端票，前端这份 spec 按"这些接口最终会长成什么样"的合理假设设计，字段细节等后端票落地后回填
- 建议后端准备至少 2-3 个不同角色/部门/数据范围的种子演示账号（例如 admin=ALL、部门经理=DEPT_AND_SUB、普通员工=SELF），"同一个问题不同用户看到不同结果"这个核心演示点才立得住，也是这份 spec 里 user story #21 的前提
- 图表渲染沿用"后端生成图片 URL + 前端 `<img>` 展示"而不是接入 ECharts 做前端交互式图表，降低前端复杂度和依赖面，和 v1 spec 里"不引入重量级组件库"的取向一致；图表的可信度由后端图表生成服务保证，不是前端的职责
- 和 v1 spec 一样，本 spec 的对话渲染扩展直接依赖 v1 spec 里"后端前置依赖"提到的 SSE 流式改造——这两份 spec 共享同一个前置依赖，不是各自独立的
