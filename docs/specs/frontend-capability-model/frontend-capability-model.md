## 0. 这份文档解决什么问题

`ChatView.vue` 把四个模式（深度研究 / 生成 PPT / 数据分析 / 联网搜索）做成同一排 chip，但这四个东西的作用域完全不同：一个是独立 Agent（换执行器）、两个是异步任务（独立链路）、一个是工具开关（叠加）。**把三种作用域做成同一种交互，是当前所有混乱的源头。**

叠加上模式发送后立刻复位（`ChatView.vue:100` 的 `pendingMode.value = undefined`），产生了一条静默失败链路：用户点"数据分析"问一句 → 追问时模式已悄悄没了 → 模型没有数据库工具 → **编造演示数据画出图表，画完才补一句"这是模拟数据"**。演示时这一幕点两下就能复现。

## 1. Scope

前端交互层的重构：Agent 层会话级绑定与常驻标识、任务层从"模式"改为"动作"、开关层归位、普通对话里的数据问题引导卡片。

**不含**：任何后端改动（六个分析工具改常驻、`ConversationDigest`、图表数据来源校验都在后端侧，各自独立推进）；不含新增后端接口。

## 2. User Stories

1. 作为用户，我想在任何时刻都能看到当前会话属于哪个 Agent，而不是发完一条消息之后就不知道自己在哪
2. 作为用户，我想我选定的 Agent 在整个会话里保持有效，追问时不需要重新点一次
3. 作为用户，我想一眼看出哪些按钮是"切换会话性质"的、哪些是"发起一个任务"的、哪些是"开个工具"的
4. 作为用户，我想在会话列表里直接看出每个历史会话是普通对话还是数据分析
5. 作为用户，我在普通对话里问了一个需要查真实数据的问题时，希望被明确告知"这里没有数据库工具"，并且能一键开一个数据分析会话——而不是拿到一份编造的数据
6. 作为用户，我发起 PPT / 深度研究任务时，希望知道它会不会带上当前会话的上下文，并且能看到带过去的是什么

## 3. Implementation Decisions

### 3.1 三层的空间分配：位置编码作用域

位置越靠上、越靠外，作用域越大。用户不读文档也能感知边界。

```
┌─────────────┬──────────────────────────────────────────────┐
│ + 新建会话   │  ⌁ 数据分析                     [基于此会话新建]│ ← Agent 层（会话头部）
│             ├──────────────────────────────────────────────┤
│ 会话列表     │                                              │
│ ⌁ 上月营收   │   对话流（含工具卡片、任务卡片）                │
│ ○ 周报草稿   │                                              │
│  ↑Agent标记 ├──────────────────────────────────────────────┤
│             │ [▣ 生成PPT] [⌕ 深度研究]      ◎联网搜索  📎文件 │ ← 任务层=动作／开关层=状态
│             │ ┌──────────────────────────────────────────┐ │
│             │ │ 今天想完成什么？                          │ │
│             │ └──────────────────────────────────────────┘ │
└─────────────┴──────────────────────────────────────────────┘
```

| 层 | 成员 | 位置 | 视觉 |
|---|---|---|---|
| Agent | 普通对话 / 数据分析 | 会话头部 | 常驻只读标识；空会话时才是可切换的选择器 |
| 任务 | PPT / 深度研究 | 输入框动作区 | **按钮**，无 active 态（点击即发起，不改变会话状态） |
| 开关 | 联网搜索 | 输入框动作区右侧 | toggle，有 active 态 |
| 基线 | 文件读取 | 无 | 不出现在交互里 |

### 3.2 Agent 锁定点：首条消息发出的那一刻

这是现成的最自然的锚——会话在首次 `send` 之前没有 `conversationId`（`chat.ts` 的 `acceptConversation` 那时才生成）。

- **空会话**：Agent 选择器可用，随便切
- **首条消息发出**：锁定，选择器原地变成只读标识
- 用户不会感到被限制，因为限制发生在他已经做出选择之后

**删掉 `pendingMode.value = undefined`。** 模式从"消息级一次性"改为"会话级持有"，`chat` store 里与 `conversationId` 并列存一个 `agentKind`。

### 3.3 默认 Agent = 普通对话

零摩擦，且多数会话确实是普通对话。数据分析靠 3.5 的引导卡片进入，不要求用户先懂得选。

### 3.4 存量会话：一律标为普通对话，不做迁移

**这是有意识的取舍，不是遗漏。** 存量会话没有 `agentKind`，其中一部分的消息历史里有 `execute_sql` 之类的工具调用记录，与普通对话的工具集不一致——理论上继续在里面对话仍会踩到"历史里有当前不存在的工具"。

不做迁移的理由：存量全部是开发期数据，价值低于"扫 `agent_trace` 找出含分析工具调用的会话并回标"的实现与验证成本。新会话从这次改动起行为正确即可。

如果后续真的需要，迁移是一次性脚本，不影响本次设计。

### 3.5 引导卡片：把三件事串成一个动作

普通对话里识别到数据问题时，在对话流里插一张 inline 卡片（不是 toast，toast 会消失、不可回溯）：

> 这个问题需要查询真实数据。当前会话是普通对话，没有数据库工具。
> **[用数据分析新建会话]**

**识别用关键词，不上 LLM**——沿用 `PptIntentRecognizer` 的既有结论（踩坑点 #52）：判定成本低、行为可预测、能讲清楚依据。多一次 LLM 调用换来的语义理解，在这个场景不值得。

这一下把「R5 提示切换」「会话级绑定的体验代价」「引导用户进入正确的 Agent」串成了一个按钮，用户不需要理解为什么要开新会话。

**本期先做不带摘要的版本**（新建一个空的数据分析会话）。带上下文摘要依赖后端 `ConversationDigest`（R15），后端就位后再补，接口上预留参数。

### 3.6 任务的上下文提示

在已有会话里点击「生成 PPT」/「深度研究」时，按钮下方展示一行说明，并且**摘要内容必须可展开查看**：

> 将带上本次会话的上下文摘要　[查看]

理由：这是一条真实的跨能力数据流（分析数据 → PPT → 对象存储），现在完全不可见。让用户看见自己传出去了什么，是这个功能能被信任的前提。

同样依赖后端 `ConversationDigest`，本期只做占位：后端未提供摘要时不显示这一行，不显示假信息。

## 4. Testing Decisions

- 组件测试参照现有 `SqlToolCard.spec.ts` / `ResearchReportCard.spec.ts` 的风格，`vitest` + `@vue/test-utils`
- **必须有的回归**：现有 `ChatView.spec.ts` / `chat.spec.ts` / `interaction.spec.ts` 全绿
- 关键行为断言：① 首条消息发出后 Agent 选择器不可变；② 同一会话连续两条消息带的 `mode` 一致（这是本次修复的核心，必须有断言钉住）；③ 切回历史会话时 `agentKind` 正确恢复
- 关键词识别是纯函数，单独单测（正例 + 反例，反例要覆盖"提到数据但不是查询请求"这类）

## 5. Out of Scope

- **后端改动**：六个分析工具改常驻（R1）、`ConversationDigest`（R15）、图表数据来源校验（R16）、视觉能力做成 `view_image` 工具——都是独立推进的后端工作
- **存量会话迁移**——见 3.4
- **意图路由自动接管**——`requirements.md` §7 已定：不做，留到 Phase 8 SubAgent 机制就位后按 Agent as Tool 形态评估
- **多模态相关的前端展示**（`view_image` 步骤条、图片预览）——等后端工具落地后单开
- **移动端适配**——现有前端本来就没做，本次不引入
