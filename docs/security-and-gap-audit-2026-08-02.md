# 当前实现偏差与安全审查（2026-08-02）

> **2026-08-05 更新**：本文档提出的两个 P0 里，第一个（未认证/IDOR）已经关闭，见文末更新记录；
> 第二个（Redis 任务锁未接线）复查后仍然成立，保留为开放项。

## 范围与结论

本次为静态审查：对照当前源码、配置和架构说明检查会话隔离、资源访问、长任务与输入边界；未使用真实密钥发起外部调用，也未替代部署环境的渗透测试。结论是：当前工程适合作为单用户/受信任开发环境，不具备多用户生产上线所需的身份、授权和资源配额边界。

## ~~P0：未认证的资源访问与会话越权（IDOR）~~ —— ✅ 已关闭（2026-08-05）

- 所有 `/agent/v1/**` 控制器均未接入认证、授权或用户上下文；普通对话在 `AgentLoopController` 中固定使用 `"anonymous"`。
- 客户端可自选 `conversationId`，而会话详情只按该值查询；会话列表也直接返回所有会话。知道或猜到 ID 的请求方可读到提问、回答、思考内容和时间线。
- 文件内容只按递增的 `fileId` 查询，不校验发起方和文件的 `conversation_id`；PPT 的恢复与下载同样只按递增的 `taskId` 查询。因此可枚举并读取他人文件解析结果、研究内容或 PPT，甚至触发他人的 PPT 续跑。

修复基线：接入认证，服务端从可信主体取得 `userId/tenantId`；在会话、文件、PPT 任务每次读写前做所有者校验，并在数据库中持久化所有者/租户字段及复合索引。客户端提供的 `conversationId` 只能是业务键，不能充当授权凭据。

**修复状态**：`SaTokenConfig` 现在对 `/agent/**`、`/api/**` 全局默认拒绝（`SaInterceptor` + `StpUtil.checkLogin()`，只放行 `/api/auth/login`），不再有匿名入口；文件内容/删除按 `belongsToUser(fileId, userId)` 校验（`FileUploadController`），PPT 的 `resume`/`status`/`download` 按 `pptGenerationService.describe(userId, taskId)` 校验所有者，均验证过对跨用户请求返回 404 而不是数据（回归测试见 `FileUploadControllerTest`）。

## P0：会话隔离的设计与部署实际不一致 —— ⚠️ 复查后仍然开放（2026-08-05）

`RedisTaskLock`、`RedisInterruptBroadcaster` 和续期能力已存在，但生产配置通过 `new AgentTaskManager()` 创建纯内存任务管理器，未注入 Redis 锁或广播器。多实例时同一会话可被不同实例同时执行，停止请求也无法跨实例生效；两个执行流可能同时写入会话历史或重复执行带副作用的工具。

修复基线：生产装配中创建并注入 Redis 锁与广播器，启动自动续期；为锁失效、广播失败、实例崩溃和双实例竞争写集成测试。部署文档和面试材料在验收前应标注为”组件已实现、未接线”。

**复查结果**：`AgentLoopExecutorConfig.agentTaskManager()` 目前仍是 `return new AgentTaskManager();`，没有变化；反而 `capability.analytics.config.AnalyticsSchemaConfig` 已经在用同一套 `RedisTaskLock` 给 schema 刷新加锁了——组件在，主线没装。列入技术债清算清单，优先级和 Analytics 的 ReAct 失败熔断并列。

## P1：缺少输入与资源配额，长任务容易被耗尽

- `AgentChatRequest`、`DeepResearchRequest`、PPT 请求和上传请求没有 Bean Validation、长度或频率限制；外部请求可反复触发昂贵模型、搜索、图表、PPT 和 Python 渲染。
- 上传接口没有业务层的文件类型白名单、解析前大小策略或解压/解析预算。图片路径直接 `readAllBytes()`，文本由 Tika 解析并可能完整落库；即使容器默认 multipart 上限存在，也不能覆盖压缩包解压膨胀、解析 CPU、数据库空间和向量化成本。
- Deep Research 与 PPT 是同步 HTTP 长流程，未接入任务管理器、客户端取消或服务端队列/并发配额。并发请求会占用虚拟线程、LLM 配额和外部服务连接。

修复基线：按用户/租户设速率、并发、token、任务数和文件配额；使用 `@Valid` 与显式字段上限；上传前做扩展名/MIME/魔数校验，给 Tika 和解压过程设置大小、递归深度和耗时预算；将长任务改为可查询的持久化任务并放入有界执行队列。

## P1：生产安全控制尚未接线

当前依赖中未见 Spring Security 配置、CORS 策略、CSRF/会话策略、审计主体或管理端点隔离。前端请求也不携带认证信息。系统中的 `user_id` 字段和记忆能力均因固定 `anonymous` 失去多用户隔离意义。

修复基线：明确认证方式（企业 SSO/OIDC 或服务端会话）、最小权限角色、CORS 允许源、Cookie/CSRF 或 bearer-token 策略，并将审计记录绑定到真实主体。上线前加入未登录、跨租户、越权下载与越权停止的端到端测试。

## P2：工具与产物边界需要在启用前收紧

- `FileSystemTools` 和 `GrepTool` 的默认沙箱为 `PathSandbox.unrestricted()`；`BashTool` 明确具备 JVM 进程同等权限。它们目前不在生产对话工具列表中，但一旦被接入用户可控 Agent，提示注入即可转化为任意文件读取/命令执行风险。
- PPT 下载虽避免把服务器路径直接交给前端，但当前没有所有权校验；其输出路径来自任务存储，后续引入后台管理写入或迁移脚本时要保持路径白名单验证。

修复基线：对外工具默认拒绝，按 capability 显式启用；文件工具必须使用受限根目录；命令工具只应在隔离执行器、审批（HITL）和命令/网络策略下运行。下载接口在鉴权后再校验任务所属会话及所有者。
